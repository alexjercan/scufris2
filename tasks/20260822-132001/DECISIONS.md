# Implementation decisions (v1)

Decisions taken while implementing the v1 scope. The architecture decisions in
`TASK.md` were settled at the 2026-08-24 pairing and are not revisited here.

## Workspace shape

`desktop/` holds two crates instead of one:

- `scufris-control`: the control protocol, with no GUI, audio, or Tauri
  dependency. It compiles and tests in seconds, which is what makes the protocol
  cheap to verify and cheap to extend for v2 session mirroring.
- `scufris-desktop`: the Tauri companion.

This mirrors `dashboardd-desktop-control` and `dashboardd-desktop`, which the
task named as the model for the protocol.

Edition 2024 and `unsafe_code = "forbid"`, matching dashboardd. Stable Rust
rather than dashboardd's nightly, because nothing here needs it and
`rustPlatform.buildRustPackage` then works without a toolchain input.

## The interaction is a pure state machine

Every accepted interaction rule lives in `scufris-desktop/src/state.rs` as
`Companion::apply(Event) -> Vec<Action>`. It owns no window, socket, or audio
handle. The runtime in `app.rs` only executes the actions.

The reason is verification. Fast send, editable review, cancellation, focus
restoration, transcription failure, retained transcripts, stale
acknowledgments, and every tray state are covered by unit tests that need no
display, microphone, or backend. Only the glue needs live playtesting.

## Which signals become which assistant state

The task named five daemon states but not their sources. Each is bound to an
event that already exists rather than to a new mechanism:

| Source                                        | State       |
| --------------------------------------------- | ----------- |
| `agent_start` / `agent_settled`               | `working`   |
| Speech playback start and finish              | `speaking`  |
| A delegated worker reported `blocked`         | `attention` |
| A delegated worker reported `failed`          | `error`     |
| A submitted transcript could not be delivered | `error`     |

`speech.ts` and `orchestration.ts` emit signals on `pi.events`, following the
existing `ACKNOWLEDGMENT_STATE_EVENT` precedent, so neither module learns about
the socket. `AssistantStateTracker` resolves them.

An active run wins over everything, because it is what the user just asked for,
and starting a run clears an unattended job signal.

Rejected: reusing `ACKNOWLEDGMENT_STATE_EVENT` for `attention`. That flag is a
model-side tool-batch gate, not a call for the user.

## Only the popup opens the socket

Gated on `SCUFRIS_DAEMON=1`, exported by `nix/popup.nix`. `SCUFRIS_ROLE` is
already `orchestrator` for every foreground session including terminal ones, so
it could not distinguish the popup, and two orchestrators would then fight over
one socket.

The daemon also probes an existing socket before binding: a live peer means it
refuses to start, a refused connection means the file is stale and is replaced.

## Undelivered submissions

Protocol v1 has no negative acknowledgment and the message set is fixed. Two
mechanisms cover the gap without adding a message type:

- The daemon reports `state: error` with the reason, so the tray shows it.
- The companion retains the transcript if no `ack` arrives within 15 seconds.

Either way the pill keeps the accepted text and `Enter` resends it. Activation
is ignored while a transcript is retained so it cannot be recorded over.

## Tray icons are drawn, not shipped

`tray::icon_rgba(state)` renders RGBA at runtime from the state name. Nine
states would otherwise mean nine image files to keep in sync with the code, and
the drawn version is directly testable: the tests assert that every state has a
distinct colour and that recording always draws the red privacy ring.

## Outside effects are absolute executables

"Open chat" and "restart backend" are `SCUFRIS_DESKTOP_CHAT_COMMAND` and
`SCUFRIS_DESKTOP_RESTART_COMMAND`, absolute paths run with no arguments and no
shell. Relative paths are rejected at startup. The menu items are disabled when
a hook is absent.

The restart hook is generated by the Home Manager module and names only
`scufris-popup.service`, which is how "restarts only the owned backend service"
is enforced rather than merely intended. It is bounded to three restarts per ten
minutes inside the companion.

No chat hook ships by default. Scufris builds no window manager, so the desktop
session supplies the i3 command.

## Bundled whisper-server

Follows the Piper precedent. Default port 10302, not the 10301 that nix.dotfiles
already uses for Pi's `voice-stt`, so the bundled server and the existing one can
coexist. `stt.whisper.enable` defaults to `stt.endpoint == null`; setting both is
an assertion failure.

The pinned default model is `ggml-base.bin` (148 MB) rather than the 1.1 GB
`large-v3-turbo` nix.dotfiles pins. A default that ships to any Nix system
should be small; a machine that wants the larger model overrides the option.

The checks substitute a stand-in package and model so `nix flake check` does not
download the real model.

## Round two: independent review findings

The first independent review (job `e0cb2bc500f5`) found four material
failure-path defects. All four are fixed; these are the choices behind the
fixes.

### An accepted transcript is durable, not in-memory

The completion criterion requires the companion and the backend to fail
independently without losing accepted unsent text. The first implementation
held review and retained transcripts only inside `Companion`, so a systemd
restart dropped them.

`PendingStore` now owns a private file, written atomically by rename and
removed only on an explicit discard or a matching acknowledgment. `App::start`
loads it and reopens the pill on the recovered transcript.

Rejected: persisting on shutdown. A crash is exactly the case that matters and
it runs no shutdown path, so the write happens when the transcript is created.

### The runtime became a set of ports

Findings 2 and 4 are runtime failures, not state-machine ones, and the runtime
had no tests because it needed Tauri, a microphone, and a socket. `App` now
takes `Ports`: surface, recorder, pending store, transcriber, executor, and the
two hooks. The real adapters live in `main.rs`; the tests use fakes.

The executor is what makes the tests deterministic rather than timing-based.
`spawn_after` lets a test fire the acknowledgment timeout on demand, and the
pill animation loop is a separate method the test executor simply drops.

### One identifier per transcript, and a bounded daemon-side set

A dropped connection between delivery and acknowledgment is indistinguishable
from a lost submission, so the companion must retry. Under the old code every
retry minted a new identifier, so the retry could enter the conversation twice.

The identifier is now allocated once when the transcript is produced and kept
through review edits, retries, and a restart. The daemon remembers accepted
identifiers, bounded to 256, and re-acknowledges without resubmitting.

Identifiers carry a per-process prefix because they outlive their process; a
fixed `pill-N` counter would collide across restarts and could have the daemon
suppress a genuinely new request.

Bounded rather than durable, in round two. Superseded below: the re-review was
right that a daemon restart is the exact failure the completion criterion names,
so the set is now durable for the authoritative session.

### Companion-local failures are visible in the tray

Fixing finding 2 surfaced a related defect the review did not name: `Failed` and
`Retained` fell through to the daemon's resting state, so a local error or a
stuck transcript showed as `idle`. The tray now reports `error` and `attention`
for those phases.

## Round three: re-review findings

The re-review (job `4bba52f00a85`) found six further defects. All six are fixed.

### Storage failures are reported, and gate the submission

`PendingStore` operations return typed results. `App::handle` runs a batch of
actions in order and stops at the first failure, so `Submit` never runs after a
save that did not land: the pill retains the text, says why, and stays editable
because nothing was delivered.

`load` distinguishes "no record" from "a record I cannot read". Collapsing the
two is what would let the next save destroy a transcript silently, so an
unreadable record opens the pill on a visible error instead.

A removal that keeps failing is retried once and then logged rather than
reopening the pill the user just finished with. The record it leaves is
recovered on the next start and resent under its original identifier, which the
now-durable daemon suppression makes harmless.

### Captures carry a generation

A stream error is only honoured while its capture is the current one. Retiring a
capture retires its right to report, so a late error from a finished recording
cannot take down the recording that replaced it.

The error can also arrive inside `Recorder::start`, before there is anywhere to
put the handle. `start_recording` checks for that on return and closes the
capture itself, which is what releases the microphone instead of leaving it open
and unreachable.

### One delivery per identifier, durably

Three separate problems, one theme:

- Concurrent retries raced the check-await-remember sequence. Deliveries are now
  keyed by identifier in an in-flight map; duplicates await the same outcome, and
  a failure removes the reservation so the next retry proceeds.
- Suppression was process-local. Each accepted submission is now recorded as a
  session entry and the set is rebuilt from the session when the socket opens, so
  it survives a daemon restart that resumes the session. This round recorded the
  submission after delivery and accepted a duplicate window as "the lesser
  failure"; the next review was right that this does not meet the completion
  criterion, and the intent/commit design below removes the window instead of
  trading it away.
- Suppression by identifier alone let an edited retry be acknowledged while only
  the original body was in the conversation. The digest is stored with the
  identifier, and a reused identifier carrying different text is refused.

### An ambiguous retry is frozen

`Retained` now records whether the submission ever left the companion. A refused
write is editable; an unacknowledged one, and anything recovered from disk, is
not, and `Enter` resends exactly what was accepted.

Rejected: leaving it editable and relying on the daemon's refusal. That turns a
preventable mistake into an error the user has to understand.

### Socket ownership is atomic

The listener binds to a private path and is hard-linked onto the public one.
`link` fails when the name exists, so a race has exactly one winner. A stale
socket is removed only after being proven dead and only while it is still the
inode that was probed, and `stop` removes the socket only if it is still the one
this process created. Every failure after `listen` closes the listener.

The concurrent-start test earned its place immediately: it caught a collision in
the private path name, which had used millisecond granularity, and which made
three simultaneous starts fight over one inode.

## Round four: re-review findings

The third review (job `bcf747dce447`) found six more, the first of which was
architectural. All six are fixed.

### Acknowledgment now follows observed acceptance

The previous rounds acknowledged a submission once `host.submit` returned. That
was wrong: `pi.sendUserMessage` is fire-and-forget. The extension-facing wrapper
in Pi 0.84.2 starts the send and catches its rejection out of band, so the call
returning means only that a send was started. Preflight, input hooks,
compaction, and queueing can all refuse it afterwards, and a queued steer lives
in process memory until the agent takes it.

The fix reads the session instead of trusting the call. `SessionAcceptance`
writes an intent entry, sends, waits for a user entry carrying that exact text
to appear in the branch, then writes a commit entry. Only then is the submission
acknowledged. `message_end` wakes the wait; the branch is the authority.

Reconciliation on start makes every crash boundary decidable:

- commit present: accepted.
- intent present and the message is in the branch: the daemon died between
  landing and committing, so accepted.
- intent present and no matching message: the send never landed, so the
  identifier stays free and the retry goes through.

That third row is the queued-steer case the review named, and it is why an
intent alone must never suppress a retry.

Rejected: awaiting Pi's internal promise. Extensions cannot reach it. Rejected:
tagging the message text with an identifier - that would put companion
bookkeeping into the conversation the user reads.

Landing was matched by digest membership over the whole branch. Rounds five and
six narrowed this: position was not enough either, and text is not evidence of
origin at all.

### Suppression follows persistence, never precedes it

`ControlHost.deliver` owns intent, send, landing, and commit, and rejects if any
of them fails. The server marks an identifier accepted only after `deliver`
resolves, so a commit that could not be written leaves nothing suppressed in
memory either. The previous code updated its local map first, which let a
same-process retry be acknowledged against a record that was never written.

### In-flight deliveries are keyed by body, not just identifier

Two clients sending one identifier with different text both awaited the same
promise and were both acknowledged, so the second was told its words landed when
only the first's did. The in-flight map now stores the digest beside the
promise, and a conflicting body is refused whether the identifier is accepted or
still in flight.

### Stale-socket takeover is serialized

The atomic `link` only protects an absent pathname. With a stale socket, every
starter sees the same dead inode, and one could remove it after another had
replaced it with a live one. Probe, removal, and claim now run while holding a
lock file created with `wx`, which is atomic. A lock whose owner is dead is
broken so a crash cannot wedge the next daemon.

Ownership is recorded immediately after the claim, and any later failure removes
the public pathname only while it is still that inode. Previously a failure in
session reconstruction left the claimed path behind as an unreachable socket.

### A discard is final

Escape now emits `DiscardPending` rather than `ClearPending`. Removal is tried
first; if it cannot happen, a tombstone record replaces the transcript, which is
enough to stop discarded words being restored. Only when neither is possible
does the pill reopen to report that the text is still on disk.

Rejected: reporting without a tombstone. The user would be told, and the words
would still come back on the next start.

Acknowledgment cleanup keeps the softer behaviour - retry, then log - because a
record left after an acknowledgment is resent under its original identifier and
suppressed. A discard has no such backstop, which is why the two are now
different actions.

### A late acknowledgment retires a retained transcript

Not in the report, but exposed by the acceptance change: a busy agent can take
longer than the companion's fifteen-second wait, so the acknowledgment arrives
while the pill is already in `Retained`. That now closes the pill and clears the
record instead of being ignored.

## Round five: re-review findings

The fourth review (job `5e4b41ee1483`) found three more. All three are fixed.

### Landing is positional, and each message is claimed once

Matching an intent against "some user entry with this digest" was wrong in two
ways. Text already in the conversation satisfied a brand-new submission
immediately, so a send that was only queued - or outright rejected - was
acknowledged anyway. And two submissions carrying identical words both consumed
the same single message.

`allocateLandings` now walks the branch in order. An intent is satisfied only by
a user entry recorded _after_ it, each entry is allocated to at most one intent,
and where several wait on the same words the oldest is served first. Live
waiting and restart reconciliation share that one function, so they cannot
disagree.

A fresh intent for an identifier supersedes its own earlier unsatisfied one,
which is what a retry after a restart writes.

### The lock is owned by inode, not by name

Removing an abandoned lock by pathname let two starters break the same dead
lock, one acquire, and the other then delete the live acquisition. The lock now
carries a token, its identity is captured with `fstat` on the handle that
created it, and release removes only that inode.

Breaking an abandoned lock moves it aside with `rename`, which is atomic, and
then confirms the moved file is the one that was inspected. A lock created in
between is put back rather than destroyed.

An empty lock - a process killed between `open(wx)` and writing its owner -
previously wedged every later daemon forever, because it had no pid to check.
It is now recoverable once it is older than a grace period, which is long enough
that a lock being written right now is never stolen.

Rejected: `flock`. Node exposes no advisory locking without a native module,
which the project's dependency rules do not allow.

### Observation runs after Pi persists, and never only on events

Pi awaits extension `message_end` handlers and appends the entry afterwards
(`agent-session.js:138-152`), so reading the branch inside the handler misses
the very message being waited on. Acknowledgment then depended on some later
event, which could be minutes away or never arrive.

The observer now runs on the next tick, and a pending delivery also re-reads the
session on a short interval. The interval is the part that matters: it makes the
acknowledgment independent of whether Pi emits anything else at all.

The test fake now reproduces Pi's ordering exactly - event first, append second -
because a fake that appended first is precisely what hid this.

Replacing or shutting down the session now settles every pending delivery with a
typed error instead of leaving its timers and closures alive.

### Messages are no longer serialized per connection

Not in the report, but exposed by the two-identical-submissions test: round four
processed one connection's messages in order, so a liveness ping could sit
behind a submission for as long as the agent took. Dispatch is concurrent again;
the in-flight map is claimed synchronously before any await, which is what makes
duplicate suppression safe without the queue.

## Round six: re-review findings

The fifth review (job `cc91b6c223c6`) found two. Both are fixed.

### Origin comes from Pi, not from the text

Positional allocation still could not tell the pill's message from words the
user typed themselves. If a manual prompt with identical text landed after the
intent and before the pill's own send, it satisfied the intent, the daemon
acknowledged, and the pill's real message arrived afterwards as a duplicate.

Pi's `input` event is the answer. It reports every prompt with a `source` of
`interactive`, `rpc`, or `extension` (`agent-session.js:785-790`), and it always
fires before that prompt can become an entry. Each prompt accepted while a
submission is outstanding now leaves a durable record of its origin:
`scufris-desktop-sent-v1` for this daemon's own, `scufris-desktop-foreign-v1`
for anything else.

Allocation is conservative. A foreign prompt claims a matching message before a
send does, so a submission is credited only when no other prompt can account for
the message. Under-crediting delays an acknowledgment and the companion retries;
over-crediting would confirm words that never reached the conversation.

That trade only works because a retry no longer re-sends while its first send is
still queued. Waiting for better evidence therefore costs nothing.

Rejected: transforming the input text to carry a marker. The `input` event can
rewrite text, and that would put companion bookkeeping into what the user reads.
Rejected: matching the message object from `message_end`. Pi records no
provenance on the message, and its own queue correlation is by text too.

### The lock never touches a replacement owner

Recovery used to move an abandoned lock aside and put it back if the identity
did not match. The review traced the sequence where that strands a live owner:
the restore can fail because a third starter has taken the free name, and the
moved lock is then deleted.

Recovery now never moves anything. The record is read, judged, and read again
immediately before removal; anything but a byte-identical token means the name
changed hands, and nothing is touched. Declining is always safe, because the
loop waits and looks again.

The token is validated as 32 hex characters, and each lock carries a lease. Both
close wedges the review found: a valid-JSON record naming an unrelated live
process, or a reused identifier, used to be respected forever. An expired lease
releases the lock whatever the record claims, and a record that is not a valid
owner at all is recoverable after a grace period.

The lease is generous next to the section it guards - a probe and two links -
so a holder that outlives it has failed, and the final socket-ownership check
still catches any overlap that follows.

## Round seven: re-review findings

The sixth review (job `50303a6e9864`) found three. All three are fixed, and the
first ended four rounds of increasingly elaborate guessing.

### The transcript carries its own identity

`input.source` is a class, not an identity: Pi marks every extension's
`sendUserMessage` as `extension`, and later handlers in the chain can transform
or handle a prompt after this one recorded its origin. The review was right that
this can misattribute in both directions.

Pi has no public way to fix that. `sendUserMessage` and `sendMessage` both
return `void`, `ctx.sessionManager` is read-only, and no event ties a prompt to
the entry it produced. So the integration changed rather than the guessing:

The transcript is now sent with `pi.sendMessage` as a
`scufris-desktop-transcript-v1` custom message carrying `details.id`. Pi
converts a custom message to a `user` message for the provider with its content
unchanged (`core/messages.js:89-96`), so the model reads exactly what was said,
and the persisted entry keeps the identifier. "Did this land" became a lookup.

Everything built for the previous answer is gone: intent, sent, foreign, and
commit records, positional allocation, conservative crediting, origin
observation. One identifier in the message replaced all of it.

The cost is honest and stated: the entry is a custom message, not a literal user
message, so the transcript view labels it as a Scufris transcript. That is the
price of a send that can be identified afterwards, and it is the same mechanism
the workflow module already uses to wake the model.

Rejected: keeping `sendUserMessage` and adding more correlation. Three rounds
showed that text, digest, position, and source class each fail, and none of them
can be fixed by another record.

### The lock is revalidated before every socket mutation

A lease can expire while its holder is stalled, and a successor can then take
both the lock and the socket. The old holder would resume and unlink the
successor's live socket, because only lock-file removal was guarded.

Every mutation of the socket pathname now re-reads the lock immediately
beforehand and aborts unless it is still byte-for-byte and inode-for-inode this
process's own. A holder that lost its lease changes nothing.

The test drives this deterministically: a child process is stalled between the
stale-socket probe and the unlink, its lease expires, a successor takes over,
and only then is the child released. Removing the recheck makes that test fail.

### One transcript bound, measured in bytes

Rust bounded the transcript in UTF-8 bytes and TypeScript in UTF-16 code units,
so 5,000 CJK characters passed the daemon and were then unreadable by the
companion's own store on restart - losing accepted text at exactly the moment it
was needed.

Both sides now measure UTF-8 bytes. The companion also validates before saving
and before sending, so it refuses what it could not read back rather than
writing a record that its own loader would call corrupt.

## Round eight: re-review findings

Review job `8fe508f18eb9` did not approve `00ab59c`. Four findings: a custom
message that triggers a turn skips the whole prompt preflight; both lock release
paths still check a pathname and then unlink it; a conflicting retry outside the
bounded cache was acknowledged; and the popup showed an internal type as a
message label.

### A spoken prompt is an ordinary prompt

`pi.sendMessage(..., { triggerTurn: true })` calls `_runAgentPrompt` directly
(`agent-session.js:1068-1090`). No `input` handler runs, no pre-send compaction
check runs, and `before_agent_start` never runs - which is where Scufris installs
the foreground identity, the live delegated-job context, and the final-response
policy. A voice request could therefore reach the model as base Pi, or under a
system prompt left behind by an earlier turn.

There is no hook that a custom-message turn executes and that can set a system
prompt: `before_agent_start` is emitted only from `prompt()`, and neither
`context` nor `before_provider_request` can replace one. The turn must therefore
come from `prompt()`, so the transcript is submitted with `sendUserMessage`. A
spoken request now gets exactly what a typed one gets, including steering into a
turn that is already running.

Input security is decided, not inherited: desktop input is declared as extension
input, passes through the whole `input` handler chain, and is exempt from
nothing. A handler that rewrites the words means no landing is ever observed, so
the transcript is retained rather than acknowledged - the safe direction.

### A receipt identifies the send, and the words prove it landed

The transcript can no longer carry its own identity, because it is a user
message now. Pi announces every prompt as an `input` event, in delivery order,
with its source. The daemon records that announcement and, when the matching
prompt lands, appends a `scufris-desktop-transcript-v1` custom entry in front of
it. Pi appends that entry immediately before the message itself
(`agent-session.js:368-380`), and a custom entry never enters the model's
context.

A landing is therefore a receipt followed by exactly the words it claims.
Neither half is enough: a receipt alone means only that a send was announced, and
a user message alone could have been typed. Identical words typed by hand are
matched to the announcement that came first, which is Pi's account of the order
rather than a guess from the text.

Rejected: keeping the custom message and moving the Scufris policy to a hook
custom-message turns do execute. The only such hook is `context`, which would
move the identity out of the system prompt for every turn in the product, to fix
one path.

### Every body a reused identifier landed is acknowledgeable

Startup rebuilds only the newest 256 identifiers. For an older one, delivery
reached the session, which treated any entry with that identifier as the landing
without comparing the words - so a retry with different text under an evicted
identifier was acknowledged although only the old text existed.

Landing lookup now returns the digests a branch actually holds for an identifier,
and a body that is not among them is refused whatever the cache remembers. A
branch can hold one identifier over two different sentences; both are in the
conversation, so both are acknowledgeable and nothing else is.

Companion identifiers are drawn from the operating system's randomness rather
than a process identifier and a clock, which are reused and can move backwards.

### The lock is the kernel's, not a file

Both release paths read a pathname and then unlinked it, so a successor could
take the name in between and lose its lock to a departing holder. A read
immediately before an unlink is not an ownership-conditional unlink, and no
POSIX call makes it one.

The lock is now a Linux abstract-namespace socket. The kernel binds the name to
exactly one socket and unbinds it when that socket closes or its process stops
existing. There is no lock record to expire, no staleness rule, no grace period,
and no pathname a former holder could unlink. The lease, the token, the grace
period, and the abandoned-lock recovery are all gone with it.

Every mutation of the socket pathname, including the one a departing daemon
performs at shutdown, now happens inside that lock. The tests hold a child
process at the barrier directly before each unlink and link and show that a
successor cannot reach the pathname at all, and that a holder killed outright
releases the lock at once.

### The receipt says what it is

Pi labels an unrendered custom entry with its internal type. The popup now
renders the receipt as a short note that the prompt after it was spoken through
the pill, and the transcript itself is a user message, so it reads like anything
else the person said.

## Round nine: re-review findings

Review job `ac06ce15b577` did not approve `3fe82c0`. Two findings: receipt
correlation trusted Pi's source class, so another extension's identical prompt,
a rewritten prompt, or one a later handler answered itself could consume the
pill's receipt; and the abstract-socket lock hashed the raw path string and
lives in a network namespace, so path aliases and separate network namespaces
both escaped it.

### The context identifies the send, and ambiguity is never resolved

Pi reports `extension` for every extension alike, so the source class cannot say
whose prompt a landing is. What can is the asynchronous context: Pi calls
`sendUserMessage` directly rather than scheduling it
(`agent-session.js:1854-1861`), so the announcement of a prompt arrives inside
the call that started it. An `AsyncLocalStorage` around the send therefore
carries the receipt to the announcement and to no other extension's.

That settles whose announcement it is; it does not settle which landing is that
announcement's, because a handler after this one may rewrite a prompt or answer
it outright and neither outcome is visible here. So the daemon under-credits by
rule: a landing is credited only when the announcement was this daemon's own,
carried the words the companion submitted, was the only prompt Pi had in flight,
and landed as those same words. Anything else leaves the submission uncredited,
and an uncredited submission is retained by the pill rather than acknowledged.

The cost is deliberate and named: a prompt typed while a spoken one is queued
leaves the spoken one unacknowledged even though it landed. Pi's public API
cannot say which landing is this daemon's, so the daemon retains rather than
guesses, and the person sends again.

Rejected: keeping a list of sent-but-unannounced submissions and matching by
digest. That list is exactly what another extension's identical prompt was able
to steal from, and no amount of extra accounting turns a source class into an
identity.

### The lock is a kernel lock on the pathname's own filesystem

The abstract-namespace lock had two holes. It hashed the raw configured path, so
`.../scufris/./daemon.sock` and a symlinked parent guarded different locks over
one directory entry. And an abstract name is scoped to a network namespace,
while the pathname it protects is not: two processes sharing this runtime
directory through different network namespaces both bound the name and both
believed they held the lock. Measured directly - two `node` processes, one under
`unshare -rn`, both bound it; the same two under `flock` did not.

The lock is now an advisory exclusive lock on the lock file beside the socket,
taken by `tools/desktop/scufris-socket-lock` because Node cannot take one
itself. It lives on that file's inode, so every name that reaches the file is the
same lock and no namespace hides one holder from another. It is released when
its holder ends, however it ends, so there is still no lease, no staleness rule,
and nothing to unlink. The lock file is never deleted, which is what leaves no
name for a former holder to remove from under a successor.

The socket path is canonicalised the same way - parent directory resolved,
basename kept - so a daemon given an alias guards, checks, and mutates the same
pathname as one given the direct name.

## Round ten: re-review findings

Review job `1bc51bd711ee` did not approve `ce215ca`. Two findings: reconciliation
read acceptance from what sat beside a receipt, which an orphan receipt or a
branch taken at one could forge; and deliberate under-crediting left no durable
record, so a retry after a daemon restart or the landing timeout could run the
same request twice.

### Acceptance is committed against the entry it accepted

A session is a tree. A branch can be taken at any entry, which leaves a receipt
with a stranger's prompt behind it, and a process can die between two appends,
which leaves a receipt with nothing behind it. Both look identical to a rule
that reads adjacency, and both would acknowledge words the pill never landed.

So acceptance is written the way it is read. Pi appends a prompt only after the
extensions have seen it, so the commit is written on the next tick, once that
prompt has an identifier, and it records that identifier. Reconciliation finds
the commit, finds the entry it names on this branch, and checks that the entry is
a prompt carrying exactly those words. Nothing else counts, and a record an
earlier build wrote before its prompt landed is read as a dispatch rather than as
proof of anything.

### Uncertain is a state, not a failure

Under-crediting was correct and its consequence was not. A submission that was
handed to Pi and never credited may have entered the conversation and done
whatever it asked for. Calling that "not delivered" and retrying it - after the
landing timeout, after a reset, after a daemon restart, or on an ordinary
Enter - can write the same files twice, send the same message twice, and start
the same work twice.

A dispatch entry is now written before the send, so the three answers a session
can give are accepted, uncertain, and unsent, and the daemon reads which from
the branch rather than from memory it loses. An uncertain submission is refused
with `uncertain` on the wire, answered to the companion that asked rather than
broadcast.

The pill holds it as its own state. The words are kept and shown, the outcome is
stated as unknown, and nothing sends them again on its own. `Ctrl+C` copies,
`Escape` discards, and `Enter` says what sending again could repeat before a
second `Enter` does it. That second press is the only thing in the system that
sets `force`, and the only thing that will send words that may already be in the
conversation.

Rejected: keeping the ordinary retry and documenting the risk. The task's own
completion criterion is that a retry cannot duplicate a request, and a note in a
decision record does not make a duplicated side effect acceptable.

Rejected: resolving uncertainty by looking for the words in the conversation. A
prompt with the same text may be the person's own, which is the ambiguity that
produced the uncertainty in the first place.

## Round eleven: re-review findings

Review job `7f20da8fd738` did not approve `c513278`. Three findings: a commit
was created by scanning the branch for the newest prompt carrying the same
words, which is not the prompt the event was about; a definitely refused
submission had no wire result of its own and became uncertain; and the companion
ignored the identifier on an uncertain answer, so a late answer could freeze the
wrong transcript.

### A commit names the entry the prompt became

The reconciliation rule was right and the creation rule was not. Reading the
commit checked the entry it named; writing it chose whichever entry looked like
the prompt. An append that failed, a branch taken between the event and the
deferred work, or a second identical prompt, each left a different entry sitting
where the scan looked, and the commit that resulted was internally consistent
and wrong.

Pi appends a message as a child of the leaf it holds, and it appends only after
every extension has seen `message_end`. So the place the prompt is about to take
is knowable exactly when the identifier is not: the leaf, read while the prompt
is landing. The commit is written against the first prompt that fills that
place.

Two rules keep the place unambiguous. A landing supersedes the one before it, so
a prompt that fills a place a lost append left behind cancels the commit instead
of receiving it. And the anchor must still be on the branch, so a branch taken
in between cancels it too. Every user prompt reaches this daemon as
`message_end` before Pi appends it, which is what makes the first rule complete:
the only entry that can appear in that place without superseding the landing is
the landing's own prompt. Replacing or shutting down the session cancels the
commit outright.

Rejected: committing from inside the `message_end` handler. The entry does not
exist yet, and a commit written before its prompt is the orphan this design
refuses to trust.

Rejected: keeping several landings and choosing between them. Two landings that
want one place are two landings that cannot both be right, and nothing here can
say which is. Under-crediting is the answer, as it is everywhere else in this
design.

### Refused and uncertain are two answers, not one

A submission the daemon refused before anything left it - a preflight that
failed, a dispatch it could not record, an identifier already carrying other
words - is known unsent. It was being broadcast as a daemon error state carrying
no identifier, so the companion that asked learned nothing, waited out its
fifteen-second timer, and froze editable words behind the two-Enter
confirmation that only a possibly-executed request needs.

The wire now carries `refused`, naming the submission, answered to the peer that
asked. The companion maps it to a retained transcript that stays editable and
that an ordinary Enter retries. A failure the daemon cannot classify stays
`uncertain`, because words that may have left are not words that are known to
have stayed, and it is still broadcast as a daemon error because that is what it
is.

A forced send that is refused does not forget what was already known: the phase
carries what was known before it, so a refusal returns those words to uncertain
rather than making a request that may already have run editable again.

### An answer names the submission it answers

Acknowledgments already had to match the transcript in hand; uncertainty did
not, and the identifier was dropped before the event reached the state machine.
A companion holds one transcript at a time, and concurrent dispatch and forced
sends make a late answer ordinary, so an answer that matched nothing in
particular could freeze the transcript that replaced its own.

Both answers now carry the identifier through the wire, the link, and the event,
and the state machine applies each only to the submission it names. The runtime's
own timeout carries it too, so the pre-check it used to perform is now the same
guard as everything else rather than a second copy of it.

## Round twelve: re-review findings

Review job `43fda6a60b29` did not approve `d286767`. Three findings: the process
that mutated the socket pathname was not the process holding the kernel lock;
submission held the keyboard until an acknowledgment; and the working-tree
developer path never loaded the extension that serves the socket.

### The lock holder does the mutating

`OwnershipLock` asked "is the helper still alive?" and then did the unlink or
the link itself. That question has a stale answer by construction: the kernel
releases the lock the instant the helper dies, and Node learns of it only when
it next runs the event loop. Between those two moments a successor holds the
lock while the old daemon still believes it does, and no amount of rechecking
closes a window that exists inside the check.

So the helper does the mutation. It probes the pathname, removes a socket
nobody is serving, and links the new one, all in the process the kernel gave
the lock to. Release is the same: unlink this pathname, but only while it is
still the inode the caller names. A helper that is gone performs none of it, and
the daemon's command fails rather than falling back to doing it locally.

Rejected: rechecking liveness closer to the mutation. The check and the mutation
are two operations in two processes; moving them nearer each other shortens the
window without removing it.

### Handing the words off gives the desktop back

The accepted interaction says submission restores focus. It did not: focus
returned only when the submission was acknowledged, so a queued or slow backend
held the keyboard in an always-on-top pill for as long as a turn takes, and an
unanswered one held it for fifteen seconds more.

The pill now closes when the words are handed to the daemon, and comes back by
itself if that submission is refused or its outcome turns out to be unknown.
Which phases are on screen is derived from the phases themselves rather than
remembered in a flag, because an action list that stops early would falsify a
flag and leave the pill either stuck open or unable to close. Showing the pill
no longer re-captures the focused window when it is already up, so a reopened
pill cannot record itself as the window to go back to.

### The working-tree backend loads the extension that answers the pill

`scufris-dev` passed workflow, voice, Calm, and dashboard. The desktop extension
is the only one that serves the control socket, so the documented local path
could not have served a live companion at all, and the helper test hard-coded
the same gap. Both now include it, and the manual says how to run that backend
in the popup's daemon role.

## Round thirteen: re-review findings

Re-review job `36df4990ed48` did not approve `bf7ed48`. One finding: the pill
that closes at handoff could close over the answer that reopened it.

### The change that ran last owns the window

Two changes overlap while a transcript is handed off. `Submit` writes to the
socket from inside the action list of the phase that accepted the words, and the
daemon's answer arrives on the link's own thread. A refusal or an uncertainty
that lands in that gap moves the phase from sent to retained and puts the pill
back on screen, and then the older list, still running, carries out the
restore-focus and the hide it decided on before any of that happened. The
transcript that needs the person ends in a pill that is physically hidden, with
only the tray left to say so.

An action list is a decision from a moment that may have passed by the time it
runs, so the pill window is no longer decided in one. Where it belongs is a
property of the phase, and the runtime reads it from the phase each change
leaves behind, stamped with that change's place in the order the companion lock
made them. An older stamp that finds a newer one already recorded changes
nothing. What the pill and the tray render carries the same stamp, so a
presentation read before a newer one cannot reach the surface after it either.

The surface call itself runs outside every lock. A window operation waits on the
event loop, and the main thread runs the pill's own commands, so a thread that
held a lock while it waited would be a thread the main thread could deadlock
against. A thread that finds another already applying therefore leaves its
decision behind and returns; the applying thread carries on until nothing newer
is left. Whichever order the two arrive in, the window ends where the newest
decision put it.

The runtime does remember one thing: what it last told the surface to do. That
is not the flag round twelve rejected, which claimed where the pill was from a
list that might stop early. This is written when the operation is performed, and
it is what makes showing and hiding idempotent - reopening an open pill would
take focus back from whatever the person moved to, and restoring focus twice
would take it from wherever they moved it.

Because one thread applies decisions on behalf of the others, a surface call
that fails hands the surface back instead of keeping it claimed. Every lock here
already recovers from poisoning rather than propagating it, and a claim that
outlived the thread holding it would be the one place that did not: the window
would stop at the decision before the failure and every later one would wait for
a thread that is gone.

Rejected: holding the companion lock across the action list. It would serialize
the two threads, but that list writes to a socket and drives window operations
that wait on the event loop, so the main thread would end up waiting for a lock
held by a thread waiting for the main thread.

Rejected: cancelling the superseded list's window actions. A list a newer
decision supersedes is not always wrong about the window: an acknowledgment
arriving in the same gap leaves a phase that is off screen and asks for nothing
of its own, so dropping the older hide would leave the pill up with nothing left
to close it. What is needed is not cancellation but the newest answer to where
the window belongs, and the phase already holds it.

## Round fourteen: re-review findings

Re-review job `0f877530611c` did not approve `0c5d31a`. One finding: the
production surface adapters turn every window, render, and tray failure into
success, so the ordered runtime can record a window state that never happened.

### A window is recorded by what it did, not by what it was asked

`Surface` could not report a failure, so `DesktopSurface` logged what Tauri
refused and returned, and the runtime then stored the visibility it had asked
for. Three things follow from that, and all three are wrong in the direction
that matters. A show that never brought the pill up still recorded the pill as
up, so the microphone opened behind a privacy indicator that was not there and
no later phase asked for the window again. A show that brought the pill up but
could not give it the keyboard recorded complete success, so the phase that owns
the window did not own focus. A hide that failed recorded the pill as down, and
an always-on-top pill recorded as down is one nothing will ever take down again.

The recovery test that covered this made its fake panic. Unwinding leaves the
recording store unreached and hands the surface back through the guard, which is
a different path from the one production takes: a Tauri adapter returns.

Every surface operation whose outcome a later decision depends on now reports
what it achieved, and the runtime records only that. Asking is not achieving, so
`show` asks the window afterwards whether it is up, and a window that cannot
answer counts as one that is not; `hide` asks the same question in reverse.
Between the two there is a third answer - the pill is up but did not take the
keyboard - which is recorded as neither up-and-ready nor down: the indicator is
there, so the phase may run, and the next decision that wants the pill asks the
window again rather than assuming.

A phase whose window did not come up runs none of its actions. There is nothing
left for it to do: the microphone has no indicator, and words nobody can see are
words nobody can correct. The interaction is abandoned instead - the microphone
and any transcription stop, and the tray says what happened. Nothing durable is
thrown away, because an accepted transcript reaches disk before anything is sent
and the next start recovers it.

Nothing retries the window by itself. A phase with no window has nothing to
retry into, and a loop that kept trying would be a loop that kept failing: the
abandoned state is not a phase but a fact recorded beside one, and the person's
next activation is what clears it and tries again.

The pill and the tray are the only things the companion can say anything with,
so a presentation that reached neither is tried again a bounded number of times.
It stops early when a newer presentation is already waiting, because a
presentation the companion has already left behind is worth less than the one it
is on now, and it stops at the bound because a surface refusing everything is
not persuaded by being asked forever. The next change publishes again.

Rejected: making the abandoned state a phase. Every phase that needs the person
needs a window, so a phase for having none would be a phase that must never be
put on screen - and the runtime would then put it on screen, fail again, and
abandon again. Recording it beside the phase keeps `on_screen` answerable
without a loop.

Rejected: treating a failed show as a reason to keep the transcript in memory
and retry the window on a timer. The transcript is already on disk, so the timer
would buy nothing the next start does not already give, and a pill reappearing
by itself minutes later is not the window the person asked for.

Rejected: blocking a decision that arrives while another thread is inside a
window operation, so that its actions cannot run before the pill is up. That
thread is waiting on the event loop, and the main thread runs the pill's own
commands, so the wait is the deadlock round thirteen avoided. The bound is
recorded as a limit instead.

## Round fifteen: re-review findings

Re-review job `3a92f439c282` did not approve `d3626a6`. Five findings: the
privacy invariant was still not enforced, a queued decision counted as settled,
achieved focus and always-on-top were still read as asked-for, a failed hide had
no recovery the runtime could reach, and the socket helper lost paths with
spaces in them.

### The window and what it says are one decision

Round fourteen kept two ordered surfaces: one for where the pill belongs, one
for what it renders. Two orders means two winners, so the window could be
settled by one decision while the pill rendered another, and nothing could ask
whether the state the person can read is the state the phase is in.

They are one surface now. `Surfaced` carries where the window belongs, what the
pill renders, and what the tray says, and one thread applies all three for one
decision. What the pill renders is only an indicator while the pill is up, so
the two were never independent.

### The microphone opens behind a rendered indicator, not an asked-for one

`StartRecording` now refuses unless the pill has taken a presentation that says
the microphone is open and the window is somewhere the person can see it. The
refusal is the same `RecordingFailed` a dead microphone gives, so the companion
already knows what to do with it.

The pill is the indicator, not the tray. A tray icon can be folded into an
overflow menu the person never opens, and a privacy indicator that may not be
on screen is not one. The tray is still told everything, and told separately: a
pill that refuses to render is exactly when the tray is the only thing left that
can say anything, so the two are published independently and one failing never
skips the other.

A capture already running is stopped the same way. Whenever a decision that says
`recording` reaches the surface while a capture is open and nothing on screen is
saying so, the runtime raises `RecordingFailed` against itself.

### Work waits for the thread that proves it

A caller that finds another thread on the surface still leaves its decision
behind rather than waiting - waiting is the deadlock round thirteen avoided -
but it no longer carries on as though the decision had been applied. It leaves
its follow-up work behind with it, and the applying thread runs that work after
it has driven the surface to the newest decision. So the key the person pressed
while the daemon was mid-render opens the microphone on the thread that put the
pill up, and not before.

### Asked for is not achieved, and doubtful is not seen

`show` now asks the window whether it holds the keyboard, because a window
manager may accept `set_focus` and hand the keyboard elsewhere, or later, or
never. There are three answers, not two. `Ready` is up, on top, and holding the
keyboard. `Seen` is up and on top with the keyboard elsewhere: the person can
read it, so the indicator counts. `Doubtful` is up with placement or
always-on-top refused: it may be behind whatever they are looking at, so nothing
that rests on being seen may rest on it, and a recording that finds itself there
stops.

### The runtime repairs its own window

A pill that would not go down is over the desktop with focus already given back,
so the keys the person presses reach their window, not the pill: nothing outside
the runtime can clear it. A pill that would not take the keyboard cannot be
typed into. Both are asked again by the runtime itself, on a short delay, on the
newest decision rather than the one that fell short, and a bounded number of
times: a window manager that has refused three times is refusing, and asking
forever is a timer nobody can stop. One chain runs at a time, and the next
decision asks again anyway.

This replaces round fourteen's recorded limit that nothing retries the window.
That limit was written for a phase with no window at all, which is still
abandoned rather than retried. A window that came up wrong is a different thing:
there is a pill on screen, and it is the runtime's to fix.

### A socket path is not a line of words

The lock helper read `claim <public> <isolated>` by splitting on spaces. A
socket path is whatever the person configured and `XDG_RUNTIME_DIR` is whatever
the session set, so both may hold spaces - and a directory named `scufris
desktop` made the helper claim a path that was not the one asked for, or refuse.
Commands are JSON objects on one line now, one field per value, with the helper
answering the same single words as before. JSON is already the protocol on the
control socket itself, so this is one encoding for the process, not two.

Rejected: quoting or escaping the fields of the existing protocol. It is the
same work as JSON with a parser nobody else has, for a helper that already has
`json` imported.

Rejected: making the tray count as a privacy indicator when the pill cannot
render. It would open the microphone in exactly the case where the surface the
person watches is broken.

Rejected: blocking the queued caller until the applying thread finishes. Same
deadlock as round fourteen rejected; leaving the follow-up work behind gets the
ordering without the wait.
