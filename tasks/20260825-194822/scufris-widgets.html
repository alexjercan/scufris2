Scufris Widgets

The native widget runtime inside scufris-desktop. It replaces dashboardd in this project completely: no dashboardd input, no dashboardctl, no compatibility. dashboardd was the proof of concept and stays its own project for linked browser dashboards. Here a widget does one thing: it shows something. No links, no inputs, no dashboard.

01

The pill spawns these

context // one paragraph

The pill is the mouth; widgets are the hands. Scufris says "CPU is at 90 percent" and a live CPU graph lands beside the pill while he talks. You say "set a timer" and a countdown appears. The user summons a calendar and it stays until closed. Everything below is about the widgets themselves; the pill only ever calls the same spawn verbs the user does. i3 and rofi still own application workflow: widgets show, they are not the desktop.

02

Anatomy of a widget

a couple hours, honestly

A widget is a directory: one small manifest and one frontend module. Live data comes from a backend - a named data source under desktop/backends/<id> that any number of widgets can subscribe to (review decision: backends are reusable, not per-widget). The manifest is declarative and stays small; the view is real code. Every declarative widget DSL in the prior-art sweep grew a logic escape hatch under pressure (eww wants functions, Rainmeter grew Lua, Plasma's DataEngines died), so we do not build one. 

# desktop/widgets/cpu/widget.toml
id = "cpu"
name = "CPU"
description = "Live CPU load"
width = 280
height = 120
backend = "system"  # optional; a shared source by id

No variants, no options, no ports. A widget that wants a second look is a second widget; that is cheaper than variant machinery when a widget costs a couple hours. Width and height are logical pixels; the window is exactly this size, like the pill. The backend names a source, not a file: cpu, memory, and network widgets all say "system" and share one process. 

// desktop/widgets/cpu/widget.ts (strict TS)
export function mount(
  root: HTMLElement,
  ctx: { spawn: unknown; send(action: unknown): void },
): View;

interface View {
  update(data: unknown): void;
  destroy(): void;
}

The whole frontend contract. The shell page owns the window chrome and the gruber tokens; the widget renders content into root and repaints on update. Data comes from the backend, from Scufris, or both - the widget cannot tell and does not care. send goes the other way: one JSON action onto the backend's stdin, so an instrument like calendar tasks takes a hand-typed entry without going through Scufris.

The shell owns what widgets share

  • Tokens. One host-injected stylesheet: gruber palette, spacing, type scale as CSS variables. Widgets style against --sw-* tokens, so one file rethemes the fleet (the Rainmeter MeterStyle / Kirigami.Theme lesson).
  • Chrome. Corner ticks in the accent color, the uppercase title, the pin tick and the close tick, the LIVE/DIM badge. Widgets never draw chrome.
  • Conduct. Opaque square panel (no compositor, no alpha - the pill already proved it), small canvases, 1-2 fps redraws. Exhibits are non-interactive except their two ticks; instruments take clicks.

Discovery: in-repo widgets live under desktop/widgets/<id>/ and are compiled into the package (build.rs walks them the way it builds the pill frontend). SCUFRIS_WIDGET_PATH adds external roots later - that is how today ships its own widget from its own repo - with dashboardd's two good discovery rules kept: directory name equals id, duplicate id across roots is a startup failure.

03

Exhibits and instruments

two postures, one runtime

A posture, not a kind. Scufris opens a widget as an exhibit: it ages on topic relevance and leaves on its own. The user opens (or pins) the same widget as an instrument: it stays until closed. Timers sit in both camps. These rules were settled at the pill design review and carry over unchanged.

Exhibit Instrument
Opened by Scufris, mid-speech, through the spawn verbs The user (pin tick, tray, a summon verb), or Scufris on request
Placement The shelf above the pill, host-positioned Initial spot near the shelf, then user-dragged, user-owned
Lifetime Ages on topic relevance, exits on its own Until the user closes it
Interaction Pin tick and close tick only; never takes focus Clickable; still never steals focus on spawn
Accent Niagara while live data flows, quartz at rest, wisteria for attention Same grammar; pinned chrome drops to bg4
04

On screen

gruber HUD language

Widget windows speak the pill's design language: square opaque panels on near-black, corner ticks in the accent, uppercase micro-titles, tabular numerals. The window recipe is the pill's, proven live: resizable window with min == max size hints (the one combination GTK honors, and exactly what makes i3 float it), focused(false) so mapping never steals the keyboard mid-sentence, always-on-top, skip taskbar, position set after show.

Workspaces follow Alex's mental model from review: an exhibit lives as if on i3's scratchpad - sticky across all workspaces, riding along with the conversation wherever you are. The pin tick promotes it: sticky drops and the widget lands on the current workspace, as if dragged off the scratchpad onto it. Handing a widget back to the runtime makes it sticky again. The mechanism is just the sticky flag; nothing touches i3's actual scratchpad.

The primary mechanism is focused(false), which maps as input=False; i3 ignores no_focus for the first window on a workspace, so the rule alone is not enough.
05

The choreography

interactive // a tiny window manager

The runtime is a small slot-based window manager, not free pixels. Widgets live in named slots: the shelf (three slots above the pill, exhibits, newest at center), the edges (four instrument slots), and the center stage (one surface, the session HUD). Every widget knows its home slot and, during a takeover, its displaced slot - so all motion is a tween between two known positions, never a collision solver.

  • Spawn: a new exhibit takes the center shelf slot; the others shift outward; a fourth retires the oldest unpinned one.
  • Takeover: opening the session HUD (click the pill) claims the center stage; shelf widgets glide to free edge slots and glide home when it closes.
  • Drag and snap: in the real thing you drag with the i3 floating modifier; the runtime watches the window settle and, if it rests within reach of a slot, glides it in. Ownership follows one sentence: the shelf is the runtime's; everywhere else is yours. Any drag that ends off the shelf pins the widget - snapped into an edge slot or standing where you dropped it - and the runtime stops aging and moving it. Dropping it back on a shelf slot returns it to the flow.

Who owns a dragged widget - decided: option A (2026-08-25)

  • A. Touch means yours (implemented above, decided in review). Any drag that ends off the shelf pins the widget; only dropping it back on a shelf slot returns it to the runtime. One sentence covers every case, and the pin tick becomes a shortcut, not a requirement. Cost: an accidental nudge silently opts a widget out of aging - the accent border is the only tell.
  • B. Slots pin, the open floor does not. Dropping into an edge slot pins; dropping in the open is a temporary shove and the runtime reclaims the widget at the next layout pass. Deliberate placements persist, accidents self-heal. Cost: "I moved it and it moved back" is the classic window manager betrayal.
  • C. Only the pin tick pins. Dragging never changes ownership; position and lifecycle stay orthogonal. Purest model, but a dragged exhibit can age out of the spot you just chose for it, which reads as the runtime overriding you.
  • D. Hold to pin. A short drag shoves temporarily; holding the drop for ~half a second pins, with the border filling in as confirmation. Expressive but undiscoverable, and misreads under i3's floating modifier where the runtime only sees the settle.
What maps to what: slot assignment, the takeover, and the retire animation are the companion's own moves (set position after show, the warm pool, and hide). The drag itself is i3's floating modifier - the runtime only watches the window settle and then either glides it into a slot or leaves it standing as yours. Nothing here fights the window manager.
06

Live data

backends // the deflisten contract

A backend is a named source, owned entirely by the companion and shared by every widget that subscribes to it. The wire contract is eww's deflisten, the simplest one that survived a decade of ricing, plus a mirror for input (review decision): one stdout line = one JSON update, fanned out whole to every subscriber - each widget renders the fields it cares about, so a cpu widget and a memory widget ride one "system" process - and one stdin line = one JSON action, written when a widget calls ctx.send. No envelope, no handshake. A backend that only reports never reads its stdin; a backend that owns something writable (the calendar tasks file) handles the action and answers by emitting the refreshed state on stdout, so a task you type by hand and a task Scufris adds travel the same loop. 

# desktop/backends/system - Python stdlib, the whole thing
# argv[1] is the spawn data as JSON; stdout lines fan out to subscribers
spawn = json.loads(sys.argv[1]) if len(sys.argv) > 1 else {}
while True:
    print(json.dumps({"cpu": cpu_pct(), "memory": mem_pct()}), flush=True)
    time.sleep(1.0)
Sharing rule: the companion runs one process per (backend id, spawn data) pair, refcounted - started when the first subscriber opens, SIGTERM when the last one closes. Widgets that pass no spawn data share the instance (cpu + memory + network on one "system"); a widget that needs its own world passes instance data and gets its own process (every timer carries its duration and start, so two timers never collide). Input rides the same sharing: an action from any subscriber lands on the one shared stdin, and the refreshed state fans back out to all of them.

Supervision - the host never trusts a widget to clean up

  • Spawn in its own process group with the PID recorded; stderr goes to journald under a per-backend target, like the pill's webview logs.
  • Close of the last subscriber means SIGTERM to the group, SIGKILL after 3 seconds, children reaped. The refcount never trusts a widget to clean up - zombie backends are the best-documented widget runtime failure (four separate eww issues).
  • Pace is coalesced in Rust: at most one push per widget per 250 ms, latest wins. A documented WebKitGTK case hit 9.5 GB from raw tick streaming; we never stream ticks.
  • Silence past 3x the widget's expected cadence renders a staleness marker on the badge; a dead backend shows a red accent and a restart tick instead of freezing the last number in place.
  • Panic verb: "clear" (and a tray item) closes every exhibit and kills every backend, provably.
07

The agent's verbs

control protocol v2

The companion already holds a live socket to the Pi daemon; widgets ride it. This is the first daemon-originated command in the protocol - every v1 daemon message is an answer or a broadcast - so v2 adds correlation ids in that direction. The version bumps to 2 cleanly; a v1 peer is refused at hello. No compatibility, by decision. 

# daemon -> companion (commands, correlated by "id")
{"v":2, "type":"widget_open",  "id":"w-1", "widget":"cpu", "posture":"exhibit", "data":{}}
{"v":2, "type":"widget_update", "id":"w-2", "surface":"widget-3", "data":{}}
{"v":2, "type":"widget_close", "id":"w-3", "surface":"widget-3"}
{"v":2, "type":"widget_clear", "id":"w-4"}

# companion -> daemon (answers echo the id; events are unsolicited)
{"v":2, "type":"widget_opened", "id":"w-1", "surface":"widget-3"}
{"v":2, "type":"widget_failed", "id":"w-1", "code":"widget_not_found", "detail":"..."}
{"v":2, "type":"widget_event", "surface":"widget-3", "event":"closed"}
{"v":2, "type":"catalog", "widgets":[{"id":"cpu", "name":"CPU", "description":"..."}]}
  • The companion owns discovery and sends the catalog right after welcome; the extension builds the typed scufris_widget_open union from it, exactly the pattern the dashboard extension proved, minus two process hops and one wire protocol.
  • Events replace polling. The 1 Hz surface-diff poll dies; the companion pushes widget_event (closed, pinned, crashed) the moment it happens, and the extension turns it into the follow-up message Calm already knows to hide.
  • Citing is updating. A widget_update - even with unchanged data - marks the exhibit cited and revives it. No separate cite verb.
  • Fixtures first: desktop/control-protocol-v2.json lands beside v1, read by both suites, before either side is implemented.
08

Inside the companion

warm pool // measured numbers

A warm pool makes spawn instant. A cold webview paints at 370-420 ms on Linux; an exhibit must land mid-sentence. So the companion pre-creates two hidden shell windows at startup; they load the shell page and idle. Spawning a widget is: send one Channel message ("become cpu", spawn data), set the size hints, show, position - a map plus one eval, well under 300 ms. The pool refills in the background.

One Channel per window. Targeted at exactly one webview, ordered by sequence numbers, cheap at our rates; payloads stay under 8 KiB. The shell imports the widget's module through a scufris-widget:// URI scheme that serves only that window's bundle - dashboardd's one clever trick, kept.

Cost, measured on this machine: 10-20 MB PSS per widget window (one WebKit web process each - fixed WebKitGTK policy), a shared network process, so five live widgets cost roughly 75 MB. Per-view processes buy crash isolation: a dying widget never touches the pill.

Long-run guard: day-scale memory growth is the documented WebKitGTK failure mode, and widgets are stateless views - so any widget whose web process passes a PSS budget is recycled through the pool, invisibly. The pill's WEBKIT_DISABLE_DMABUF_RENDERER re-exec already covers every new window.

Code shape: a widgets module beside the pill's, with the same ports-and-adapters split the pill has - the runtime holds no window or process handle directly, so lifecycle, aging, and supervision are all unit-testable without a desktop session. Widget traffic never touches the pill's Event state machine. Two config gates from the inventory: the capability file gains a widget-* label glob, and the CSP whitelists the widget URI scheme.

Decisions to review

your call, then they land in RESEARCH.md
  • The shelf. Above the pill, centered, capped at 3, oldest unpinned retires first - or do you want exhibits to a side edge instead? decided 2026-08-25: keep as designed
  • The aging trigger. "A turn completed and neither opened nor updated this exhibit" is the concrete reading of "topic change". Sharp enough, or too eager for multi-turn work on one topic? decided 2026-08-25: keep this reading
  • Backend stdin. V1 backends are output-only (SIGTERM is the whole input). Interactive instruments will eventually want a line in the other direction - add it now or when the first widget needs it? decided 2026-08-25: add it now - one stdin line = one JSON action, via ctx.send
  • Summoning instruments. Tray submenu for sure; is the second path a voice verb ("show the calendar"), a rofi entry, or a scufris-ctl verb riding the command socket the i3-mode task will build? decided 2026-08-25: the voice verb - tray + "show the calendar"
  • The note widget's reach. Plain text with emphasis and lists, or markdown-complete? Plain keeps increment 1 honest; markdown invites the exhibit to become a document. decided 2026-08-25: text only, no formatting - and a quick-capture use is on the horizon (jot a note, save it into today)
  • Widget windows on workspaces. Exhibits stick to all workspaces (they accompany speech) while instruments stay on theirs - agree? decided 2026-08-25: yes, with the scratchpad model - exhibits ride sticky like the scratchpad, pin promotes onto the current workspace
  • Drag ownership. The demo implements option A from section 05: the shelf is the runtime's, everywhere else is yours.
