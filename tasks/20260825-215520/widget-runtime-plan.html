Widget Runtime Buildout

The reviewed design (Scufris Widgets, task 20260825-194822, all seven decisions in) meets the code as it stands. This page is the plan between them: the data structures both sides gain, the one genuinely new mechanism, the file-by-file change map including the complete dashboardd removal, and the order the commits land in.

01

Where the code stands

mapped 2026-08-25

The companion is a one-window app. The only window is the pill (pill.rs, label "pill"), the only IPC is four global emit events plus six invoke commands - no tauri::ipc::Channel anywhere - and the whole binary runs on std::thread: no tokio, no async runtime. Protocol v1 (scufris-control/src/lib.rs) speaks three companion messages and six daemon messages over one Unix socket line protocol, with shared fixtures in desktop/control-protocol-v1.json that both test suites read. Every daemon-to-companion message today is an answer or a broadcast - ControlServer has no targeted request path, and the companion never writes in response to a daemon message.

The thread model is a plan constraint. dashboardd supervised backends with a tokio select loop; this companion has no async runtime and an established idiom instead (the Executor trait, a thread per concern, mutexed state). Backend supervision is planned as reader threads plus one mutexed table - matching the codebase, not the donor.
02

Target shape

one new module each side

One new module on each side of the socket. The extension gains extensions/scufris/widgets/: four tools typed from the pushed catalog, a pending map for correlated commands, and the scufris-widget-event follow-up Calm already hides. The companion gains src/widgets/ beside the pill's modules, with the pill's ports-and-adapters split: a pure runtime that owns surfaces, slots, and (later) aging, driven through ports so it unit-tests without a desktop. Widget traffic never touches the pill's Event state machine.

New surfaces, by directory

  • desktop/scufris-desktop/src/widgets/ - runtime (pure), catalog, pool, windows adapter, backends (increment 2), wire glue.
  • desktop/scufris-desktop/shell/ - the shell page: chrome, --sw-* tokens, Channel client, module loader. Own tsc project; built into ui/dist/ beside the pill.
  • desktop/widgets/<id>/ - in-repo widgets (widget.toml + strict-TS widget.ts); desktop/backends/<id> - backend scripts (increment 2).
  • extensions/scufris/widgets/index.ts - tools, pending map, follow-up events; skills/widgets/SKILL.md - the model-facing spawn policy replacing skills/dashboard.
03

Protocol v2 and the correlation machinery

the one new mechanism

The version bumps 1 to 2 in both mirrors (scufris-control/src/lib.rs:22, desktop/protocol.ts:4); a v1 peer is refused at hello, by decision. desktop/control-protocol-v2.json lands first - canonical, tolerated, and rejected lines for both sides - and both suites point at it; the v1 fixture file leaves with the bump, since no implementation speaks v1 afterwards. Ids and the 64 KiB line cap carry over; widget and surface ids validate like submission ids, and data payloads cap at 8 KiB to stay under the Channel-friendly size. 

# daemon -> companion: the first daemon-originated commands, correlated by "id"
{"v":2, "type":"widget_open",   "id":"w-1", "widget":"note", "posture":"exhibit", "data":{}}
{"v":2, "type":"widget_update", "id":"w-2", "surface":"widget-3", "data":{}}
{"v":2, "type":"widget_close",  "id":"w-3", "surface":"widget-3"}
{"v":2, "type":"widget_clear",  "id":"w-4"}

# companion -> daemon: answers echo the id; events and the catalog are unsolicited
{"v":2, "type":"widget_opened", "id":"w-1", "surface":"widget-3"}
{"v":2, "type":"widget_failed", "id":"w-1", "code":"widget_not_found", "detail":"..."}
{"v":2, "type":"widget_event", "surface":"widget-3", "event":"closed"}
{"v":2, "type":"catalog", "widgets":[{"id":"note", "name":"Note", "description":"..."}]}

Extension side. ControlServer today only broadcasts (server.ts:567) or answers inline. It gains request(body): Promise<Answer> - a targeted write to the connected companion, a Map<correlationId, Pending>, a per-request timeout, and rejection of every pending request when the companion disconnects. Tool calls await it; a timeout or widget_failed becomes the tool's error result.

Companion side. daemon.rs maps the four new DaemonBody variants to a new DaemonEvent::Widget(cmd) arm, routed to the widgets module - a sibling of App::observe, never the pill's Event enum. Answers write back through the link's existing writer (the submit() path already proves the shared writer handle); the catalog is sent once, right after hello is welcomed.

This is the plan's center of gravity. Both explorer sweeps and the design research agree: the windows are known recipes, but a correlated, targeted request/response path exists in neither direction of the stack today. It lands as its own commit with fixture-driven tests on both sides before any window code.
04

Data structures

both sides of the socket, and the shell

The companion's core is a pure runtime in the style of state.rs: commands in, actions out, no I/O, every rule unit-tested without a desktop session. Slot names come from the design page's choreography demo verbatim. 

// src/widgets/runtime.rs - pure; the host drives ports, the runtime decides
struct Runtime {
  surfaces: BTreeMap<SurfaceId, Surface>,
  shelf: VecDeque<SurfaceId>,            // newest first, cap 3, oldest unpinned retires
  edges: BTreeMap<EdgeSlot, SurfaceId>,  // instruments
  hidden_with_pill: bool,                // Q6: the scratchpad hide (increment 2)
}

struct Surface {
  id: SurfaceId,             // "widget-3"; doubles as the window label
  widget: WidgetId,
  posture: Posture,          // Exhibit | Instrument
  slot: Slot,
  owned: bool,               // Q7: any drag ending off the shelf sets it
  life: Life,                // Live | Dim { since } | Pinned (clocks in increment 2)
  backend: Option<BackendKey>,
}

enum Slot { Shelf(u8), Edge(EdgeSlot), Stage, Standing { x: i32, y: i32 } }
enum EdgeSlot { TopLeft, TopRight, MidLeft, MidRight }   // tl tr ml mr, as in the demo

// in:  Cmd::{Open, Update, Close, Clear} from the daemon; ticks and drags from the shell
// out: Act::{Adopt, Show, Move, Update, Life, Retire, Answer(ClientBody)} against the ports
// src/widgets/catalog.rs - startup discovery
struct Manifest {          // widget.toml, serde + toml crate (new dep)
  id: String,              // must equal the directory name
  name: String,
  description: String,
  width: u32,
  height: u32,
  backend: Option<String>,
}
struct Catalog { widgets: BTreeMap<WidgetId, Widget> }
// duplicate id across roots = startup failure, no shadowing

// src/widgets/pool.rs - warm shells
struct Pool { idle: Vec<Shell>, target: usize /* 2 */, next: u32 }
struct Shell { label: String, channel: Channel<ShellMsg> }
// adopt = become + size hints + position + show_passive; refill async
// src/widgets/backends.rs - increment 2, std::thread, no tokio
type BackendKey = (String, String);
// (backend id, spawn JSON with sorted keys)

struct Backends { running: Mutex<HashMap<BackendKey, Backend>> }
struct Backend {
  pid: u32,                  // own process group, recorded;
                             // SIGTERM group, SIGKILL after 3 s
  refs: BTreeSet<SurfaceId>, // last close kills the process
  stdin: ChildStdin,         // one JSON line per ctx.send action
  reader: JoinHandle<()>,    // stdout lines -> coalescer
  seen: Instant,             // stale at 3x expected cadence
}
// coalescer: latest-wins per surface, flushed at 250 ms -
// never a raw tick stream to a webview
// shell/shell.ts - the per-window Channel contract and the four invoke commands
type ShellMsg =
  | { kind: "become"; surface: string; widget: string; name: string; data: unknown }
  | { kind: "update"; data: unknown }
  | { kind: "life"; state: "live" | "dim" | "stale" | "dead" | "pinned" }
  | { kind: "retire" };  // unmount, wipe, return to the pool

// shell -> Rust, all scoped by window label:
//   widget_shell_ready(channel)          hands Rust this window's Channel
//   widget_tick(kind: "close" | "pin")   the two chrome ticks
//   widget_hover(over: boolean)          freezes aging clocks (increment 2)
//   widget_send(action: unknown)         ctx.send -> backend stdin (increment 3)

// the widget module contract, unchanged from the design page:
//   mount(root, ctx: { spawn: unknown; send(action: unknown): void })
//     -> { update(data: unknown): void; destroy(): void }
// extensions/scufris/widgets/index.ts - daemon side
interface Pending { resolve(answer: Answer): void; timer: NodeJS.Timeout }
// pending: Map<string, Pending> keyed by correlation id "w-N"
// surfaces: Map<surfaceId, { widget, posture }> from answers + events
// catalog message -> late-registers the four tools (the pattern the
//   dashboard extension proved on session_start), widget ids as a union
// widget_event -> pi.sendMessage({ customType: "scufris-widget-event", ... },
//   { deliverAs: "followUp", triggerTurn: false })  // calm.ts:15 already hides it

The four tools (increment 1)

  • scufris_widget_open - widget id union from the catalog, posture, data. Returns the surface id.
  • scufris_widget_update - surface, data. Citing is updating: an update with unchanged data revives (increment 2 makes that matter).
  • scufris_widget_close - surface.
  • scufris_widget_clear - the panic verb; closes the runtime's exhibits, leaves user-owned widgets standing.
05

Windows, serving, and the two config gates

the pill's recipes, generalized
  • The window recipe is the pill's (pill.rs:59-71): min == max size hints (i3 floats it, GTK honors the size), no decorations, always-on-top, skip taskbar, opaque, built visible(false). Two deltas: focused(false) with focusable(true) so i3 never focuses at map yet the window stays clickable, and never calling set_focus() on a widget. Showing is the show_passive() idiom; per-widget WM_CLASS instances (scufris-widget-cpu) let Alex write i3 rules.
  • Slot geometry is pure math in the bottom_center() style: one unit-tested function per anchor family (shelf above the pill, four edges, center stage), clamped to the monitor. Position after show; i3 places floating windows first.
  • Serving: the shell page ships in ui/dist/ (build.rs compiles the second tsc project and copies shell.html, shell.css, shell.js, tokens.css); windows open WebviewUrl::App("shell.html"). Widget modules compile at build time into ui/dist/widgets/<id>/widget.js and are served by a scufris-widget:// URI scheme that answers only the requesting window's current widget - dashboardd's one clever trick, kept.
  • Gate one: capabilities/default.json scopes permissions to ["pill"]; it gains a widget-* label glob. Gate two: the CSP in tauri.conf.json whitelists scufris-widget: in script-src. Both are startup-silent failures if forgotten, so both get a check.
  • New crate dependency: toml (serde feature) for the manifest. Everything else is already in the tree.

Landing order

increment 1 in five commits
  1. Remove dashboardd. Independent of everything else, the largest diff, and every suite stays green: the deletes, the edit chain, the nix ripples, the lock regen, the docs sweep. Proof: scoped grep finds no dashboardd; npm run check, python unittest, nix flake check all pass.
  2. Protocol v2, fixtures first. The v2 fixture file, both codecs, version bump, v1 fixture removed. Proof: both suites read the same fixtures and round-trip canonical lines byte-identically.
  3. Correlation machinery. ControlServer.request() with pending map and timeouts; the companion's DaemonEvent::Widget routing and answer writes. Proof: socket tests drive open/opened and open/failed end to end with a fake peer on each side.
  4. The runtime and the windows. Pure runtime with slot and shelf rules unit-tested; catalog discovery; the pool; the shell page and tokens; the note widget; both config gates. Proof: a staged widget_open maps a warm shell beside the pill without stealing focus (manual, on the live desktop).
  5. The extension. The widgets module, four tools from the pushed catalog, follow-up events, the widgets skill, launcher wiring. Proof: "show a note" lands an exhibit mid-speech; the increment 1 acceptance line is met.

Then, unchanged from the design

  • Increment 2 - live and aging: backends and supervision, the shared system backend with the cpu widget, the full exhibit lifecycle with frozen clocks, sticky exhibits with pin promoting to the current workspace, hide-with-pill.
  • Increment 3 - instruments: tray submenu + the voice verb, timer and tasks widgets, ctx.send stdin actions, SCUFRIS_WIDGET_PATH external roots.
  • Increment 4 - the session HUD as a widget on this runtime (task 20260825-153801), center stage and the displacement choreography.
08

Risks and review decisions

both details decided on this page
  • Breaking module interface. Removing programs.scufris.dashboard.* fails evaluation for any consumer setting it. Deliberate, but it needs the CHANGELOG entry and a release note.
  • Silent config gates. A missing capability glob or CSP entry fails at runtime, not at build. Both get asserted in tests (the capability file is JSON; the CSP string is in tauri.conf.json).
  • WebKit throttles hidden pages. Pooled shells and hidden widgets must act on Channel messages, never on rAF ticking - the same rule the orb work just encoded in the pill.
  • Test environment: the socket suite needs TMPDIR=/tmp under nested nix-shells (108-byte socket path cap) - this explains the 48 "failures" seen on a clean master.
decided - the turn boundary Decided on this page, 2026-08-25 (Alex: "idle means one turn ended"). The assistant state falling back to idle after working or speaking is the turn-ended signal; every exhibit Scufris neither opened nor updated during that turn starts its dim clock then. Costs no new wire message; if the inference proves unreliable in practice (states can flap), v2 gains an explicit turn-ended message - a one-variant addition. Lands with increment 2.
decided - one scratchpad, one pill Alex's model (page review, 2026-08-25): the pill and the scratchpad layer are the same thing - and the code already agrees. state.rs documents the pill as "a resident HUD: only the person's Escape puts it away, and only their activation brings it back"; an earlier framing here claimed the pill auto-hides after each interaction, which was wrong and is withdrawn. So the linked model holds with no new rule. The shelf and the edge slots belong to the pill's layer; a runtime-owned widget is visible exactly when the pill is. Escape hides the layer whole - pill and every runtime-owned widget, state intact, aging clocks frozen (the Q6 follow-up decision) - and the next activation brings it back exactly as it was. Promotion out of the layer is pinning, as decided in Q7: the pin tick or any drag ending off the shelf; a promoted widget unsticks, stays where you put it, and is exempt from Escape because it left the layer. Dropping it back on a shelf slot demotes it. Nothing here remains open; lands with increment 2.
