Scufris as a Service

The conversation stops living in a terminal window. A daemon owns pi, the session, and the socket; the desktop app becomes the microphone, the speaker, and the screen. The server moves from the agent to the service, and everything else becomes a client.

01

The inversion

Thesis

Today the Pi process in the Kitty scratchpad is the server. It binds $XDG_RUNTIME_DIR/scufris/daemon.sock, and the desktop companion connects out to it. That is why the Home Manager module asserts that enabling the desktop requires enabling the popup: without the terminal window there is no socket, and without the socket there is no Scufris.

The conversation is therefore pinned to a window. Close the window and the assistant is gone. That is the thing worth fixing, and everything in this document follows from fixing exactly that.

A new process, scufris-service, becomes the server. It spawns pi --mode rpc and owns the session. It serves one socket. Both the agent and the desktop app connect to it. No user interface owns the conversation any more, so no user interface can take it away.

02

Who owns what

Four processes

Four processes, and the boundaries are drawn so that each one can be described in a sentence. What a process does not do matters as much: a service that grew rendering or synthesis into it would be the thing this design is trying not to build.

Process Owns Never
scufris-service The session directory. Spawning and supervising the agent. The one socket and who is connected to it. Assistant state. A bounded transcript ring so a reconnecting screen has something to draw. Routing surface commands between the agent and the frontend. No audio. No synthesis. No rendering. No windows. No model calls. No tools.
pi --mode rpc The thinking. Tools, sub-agents, skills, jobs, the workflow engine, Calm policy, response shaping. Everything under extensions/scufris/ keeps running here, unchanged except for the desktop extension. Binds no socket. Owns no window. Speaks nothing aloud.
scufris-desktop Every pixel and every sample. The pill, the textbox, the HUD, the tray, the widget runtime. Microphone capture and the whisper client. Piper synthesis and playback. Hotkeys and focus restoration. Holds no conversation. Persists nothing but its own unsent words.
whisper-server Transcription over HTTP. Already a separate unit, already optional, already someone else's if you point at an endpoint. Knows nothing about Scufris.

Putting whisper and piper behind the desktop app is the decision that makes the service simple. The service handles text and only text. It cannot speak, which means a headless service is silent by construction rather than by configuration, and voice becomes a property of the machine you are sitting at rather than a property of the assistant.

The half of this that already works this way is the microphone: capture and the whisper client are in the companion today. The half that moves is piper, which currently runs inside the Pi process. The seam is clean, because the two halves of speech are already separate concerns: shaping stays in the agent, where the voice extension decides what is safe to say aloud, and synthesis moves to the frontend, which is the thing with a speaker.

03

The seams

Three protocols

Three, and two of them already exist. That is the pleasant surprise of this design: almost nothing new has to be invented, because the protocol work done for widgets was done against the right abstraction.

Seam 1 — service to agent: Pi RPC over stdio

Pi's own documented protocol, LF-terminated JSON lines on the child's stdin and stdout. Scufris already drives it for standalone Quick Review (tools/quick-review-agent), so this is a road we have walked. 

// service -> agent
{"id": "u-41", "type": "prompt", "message": "what is on my calendar"}
{"type": "prompt", "message": "...", "streamingBehavior": "steer"}
{"type": "abort"}

// agent -> service
{"type": "agent_start"}
{"type": "message_end", "message": {...}}
{"type": "tool_execution_start", ...}
{"type": "agent_settled"}

The service is the RPC client. It writes prompts and reads events, and that stream is where assistant state and the HUD transcript both come from.

Seam 2 — agent to service: the surface protocol, inverted

Tool calls originate inside a model turn and need an answer. scufris_widget_open has to return a surface identifier before the tool result is written, so it cannot ride the event stream. It needs a request and response channel, which is exactly what extensions/scufris/desktop/ already implements.

So the code stays and the direction flips. server.ts stops calling createServer and starts connecting out to the service, the way daemon.rs does today. The correlation identifiers, the five-second bound, the typed error codes, the well-formedness checks and the shared fixtures all survive. The socket lock disappears, because the service binds the socket and systemd makes sure there is one of it.

Seam 3 — frontend to service: the same socket, a second role

One socket, two kinds of client, declared in the hello. Protocol v3 is v2 plus a role and the message types the frontend needs. 

// frontend -> service
{"v": 3, "type": "hello", "role": "frontend", "voice": true}
{"v": 3, "type": "submit", "id": "u-41", "text": "..."}
{"v": 3, "type": "speaking", "active": true}   // piper started
{"v": 3, "type": "widget_event", ...}

// service -> frontend
{"v": 3, "type": "state", "state": "working"}
{"v": 3, "type": "say", "text": "..."}       // shaped by the voice extension
{"v": 3, "type": "transcript", "entry": {...}} // for the HUD
{"v": 3, "type": "widget_open", ...}

The service routes rather than interprets. A surface command from the agent goes out to the frontend and its answer comes back under the same correlation identifier. When no frontend is connected the service answers companion_unavailable itself, which is a code the widget tools already handle.

scufris-ctl becomes a client of seam 3 with a third role, control. That gives it real verbs for the first time: send, listen, cancel, abort, state, detach, attach. It works with no graphical session at all, which is how the service gets tested without a display.

04

What the stream gives us for free

Read before building

Pi's RPC events answer several questions that Scufris currently answers with code of its own. Reading the event table before writing the service removes work rather than adding it.

Assistant state stops being computed

agent_start, tool_execution_start and agent_settled are the state machine. Idle is settled, working is anything between. The desktop extension's own state derivation goes away, and so does the risk of it disagreeing with what Pi is actually doing.

Speaking becomes reported by whoever speaks

Because piper moves to the frontend, the frontend is what knows when speech starts and stops, and it says so. That is strictly better than today, where the widget ageing rule stops its clocks on a speaking state inferred one process away from the speaker.

Talking over a running turn gets a real answer

streamingBehavior: "steer" delivers a message after the current turn's tool calls and before the next model call; "followUp" waits for the run to settle. So "I said something while it was thinking" stops being an awkward case and becomes a choice with two documented behaviours.

Stop is now possible

abort ends the current run. There is no way to do that from the pill today. It becomes a verb on the ctl and a key on the frontend.

The HUD's history has a source

message_end carries complete messages, and get_entries fetches session history on demand. The service keeps a bounded ring for the common case — a frontend restarting needs the last screenful, not the last month — and asks the agent for anything deeper.

One thing that must not be skipped

In RPC mode, extension user-interface requests (notify, confirm, input, select, editor) are emitted on stdout and wait for an answer on stdin. Today the TUI answers them. If the service does not, an extension that opens a dialog hangs the agent.

Scufris extensions currently use only notify, which is fire-and-forget, so the immediate exposure is small. The service must still answer every request type — routing what it can to the frontend and replying with a cancellation for the rest. And notify stops being a line in a terminal nobody is looking at and becomes a tray notification, which is an improvement worth taking on day one.

05

Surfaces

Voice is a capability

One correction to the sketch, and it makes the rest fall into place. Voice is not a mode, and the HUD is not the other mode. They are a capability and a surface, and they compose: reading the transcript while talking is an ordinary thing to want, and a design where enabling voice hides the conversation would be one to regret.

So the frontend has four surfaces and one flag. The flag, voice, decides only whether the microphone and the speaker exist.

Surface What it is Keyboard
Pill The orb. An indicator and nothing else: listening, working, speaking, attention, disconnected. It has no keys of its own any more. Never focused
Textbox The one thing that sends. It opens empty in text mode and pre-filled with the transcription in voice mode. Same window, same keys, either way. Takes focus
HUD The Calm conversation, rendered from the transcript stream. Available whether or not voice is on, toggled by its own key. Takes focus to scroll and copy
Widgets Unchanged. The runtime stays in the frontend; its commands arrive through the service instead of directly. Never focused

The textbox being the only sender is the simplification that pays for itself. Recording is no longer a way to submit; it is a way to fill the box. You always see the words before they go, the review state and the recording state collapse into one window, and the frontend has exactly one code path from text to submit.

The cost is honest and worth naming: voice submission becomes two keypresses plus Enter, where today Enter while recording sends immediately. That is slower, and it is the trade you asked for — never sending words you have not read.

06

One turn, keystroke by keystroke

Interaction
Super+D

Advance. Nothing up: pill rises, microphone opens. Listening: stop, transcribe, open the textbox with the words in it. Text mode: open the textbox empty.

Super+Escape

Cancel the listen. Discards the recording and puts the pill back to rest.

Enter / Escape

In the textbox only, which holds the keyboard, so these are ordinary keys in a focused window. Send, or discard.

Two properties fall out of this that are worth stating plainly. The service never needs a display, so the whole conversation path is testable with scufris-ctl send and no graphical session. And the frontend never needs the agent, so it can start, show a disconnected orb, and connect when the service comes up — which is what it already does today with daemon.rs.

07

What this deletes

Subtraction

A design that only adds is a design to distrust. This one removes several pieces of machinery that exist purely because the socket is in the wrong process or because the pill has to steal the keyboard.

  • The i3 binding mode. All of keys.rs, the SCUFRIS_DESKTOP_MODE_COMMAND hook, the mode-enter and mode-leave dance, and the documentation explaining it. Bare Enter and Escape only ever needed rescuing because the pill wanted keys without holding the keyboard. The textbox holds the keyboard, so they arrive normally.
  • desktop.sock and command.rs. The companion stops being a server. scufris-ctl accept and the scufris://accept page round trip go with it.
  • The socket lock. tools/desktop/scufris-socket-lock exists because two popups could race for one socket name. A systemd service does not race with itself.
  • SCUFRIS_DAEMON and the server half of the desktop extension. Roughly the accept loop and the lock dance; the protocol and the command machinery stay.
  • The Home Manager assertion that the desktop requires the popup. The dependency it encoded no longer exists.
  • The review window as a separate state. It becomes the textbox, which is also the text-mode input.
08

What this costs

Risks

The Pi TUI goes away, and it is the best interface we have

This is the real cost and it should not be soft-pedalled. The Kitty popup is a complete Pi terminal: model cycling, thinking levels, slash commands, session forking, the config UI, scrollback, copy. RPC mode has no TUI, and the HUD will not match it for a long time.

The mitigation is an explicit handoff rather than a second writer. scufris-ctl detach stops the service's agent child and leaves the session directory free; you then run an ordinary pi --continue in any terminal against it and get everything back. scufris-ctl attach restarts the child when you are done. The service reports detached as an assistant state, so the pill says so rather than looking broken. Two writers on one session is never allowed, and the ctl is what enforces it.

The HUD is a large build hiding inside a small phrase

"Shows the Calm conversation" is a transcript renderer: streaming text, thinking blocks, tool executions, custom messages, scrollback, and a theme. It is comparable in size to the pill and the widget runtime together. Until it exists, text mode means scufris-ctl send and the detach hatch, and that has to be acceptable for a while or the increments below are in the wrong order.

The service becomes the single point

Today a companion crash is harmless and a popup crash takes the socket. Afterwards both frontends are disposable and the service is the thing that must not die. That is the trade being bought deliberately: one process to supervise, restarted by systemd, with the session on disk so a restart resumes rather than forgets.

09

Open decisions

Needs a call

D1 — Does the service spawn the frontend?

The sketch says the service starts the Tauri app as its frontend. The difficulty is that a graphical client needs the display environment and must die with the graphical session, which is what PartOf=graphical-session.target already models. A service on default.target spawning a GUI child fights that.

Recommended: the frontend stays its own unit, wanted by graphical-session.target, and connects to the service. The service still owns the relationship — it is the only server the frontend has — and can start or restart it by asking systemd when a session exists. Ownership by protocol, not by process parentage.

D2 — What is the service written in?

Three real options. Rust, in the existing cargo workspace, driving pi --mode rpc as a child. TypeScript, driving the same child, reusing server.ts nearly unchanged. TypeScript embedding AgentSession, which Pi's own documentation suggests for Node clients and which would remove the subprocess entirely — at the price of re-wiring what the pi CLI does for us: settings, extension discovery, skills, prompt templates, session resolution.

Recommended: Rust. The workspace, the protocol crate, and the supervision patterns all exist — the widget backends are already supervised exactly this way, process group and all. The RPC stream is a documented line protocol, so we couple to Pi's protocol rather than to Pi's internals, and pi keeps doing everything the CLI does.

D3 — Where does the repository put it?

desktop/ is named for the runtime architecture, and a service that is not a desktop thing does not belong under it.

Recommended: rename the workspace to native/ holding three crates: scufris-control (protocol), scufris-service, and scufris-desktop. One rename, done once, before there are two things to move.

D4 — Does the HUD replace the popup, or join it?

Related to D1 and to the first risk. If the popup unit survives as a detach target, the migration is gentle and nothing is lost early. If it is retired with the last increment, the HUD has to be finished first.

Recommended: keep the popup as a detach target from the start and retire the unit only when the HUD is genuinely better. The escape hatch costs nothing while it is unused.

D5 — What speaks, exactly?

The voice extension currently decides what is safe to say aloud and calls scufris-speak. With synthesis in the frontend it instead emits shaped text. The question is whether that travels as a surface command over seam 2, or as a field on the transcript entries over seam 3.

Recommended: a say command over seam 2, routed like any other. Speaking is an act with a lifetime, not a property of a message, and the frontend has to be able to refuse it — muted, no speaker, voice off.
10

Increments

Order of work

Each step ships and is usable before the next one starts. The order is chosen so that the risky part — a service owning the conversation — is proven headlessly before any window depends on it.

  1. The service, headless. Spawn and supervise pi --mode rpc, own the session directory, derive state from the event stream, hold the transcript ring, answer extension UI requests, serve protocol v3. scufris-ctl send | state | abort | detach | attach. No graphical change at all; verified with the ctl and a test socket.
  2. The agent becomes a client. The desktop extension stops binding and starts connecting. Widget commands route through the service. The socket lock and SCUFRIS_DAEMON go. At this point the old popup still works, now talking to the service.
  3. The frontend becomes a client. Pill, tray and widget runtime move to v3. desktop.sock, command.rs and the binding mode are deleted. Piper moves into the frontend behind the voice flag.
  4. The textbox. One focused window that sends, filled by voice or typed into directly. The review state and Enter-while-recording are removed with it.
  5. The HUD. The Calm conversation as a frontend surface, drawn from the transcript stream, with get_entries behind it for depth.
  6. Retire the popup unit and document detach as the way to a full terminal. Only once the HUD earns it.

The widget runtime is untouched by all six. It stays in the frontend, its protocol survives with one more hop in front of it, and the four tools do not change shape. Jobs, tmux, review and the workflow engine are equally untouched: they live inside the agent and never knew where the socket was.
