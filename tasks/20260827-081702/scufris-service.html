Scufris as a Service

The conversation stops living in a terminal window. A daemon owns pi, the session, and the socket; the desktop app becomes the microphone, the speaker, and the screen. The server moves from the agent to the service, and everything else becomes a client.

00

Laws

Bounds everything below

Four constraints settled before the design, each of which removes work rather than adding it. Everything in this document is written inside them, and the first one is the one that keeps the rest small.

L1 — One of everything, on one machine

One pi --mode rpc child. Never two, never a pool, never a registry. The service supervises a single process with a single session, so there is no routing by session, no switching, no fan-out, and no question anywhere in the protocol about which agent a message is for.

And one of everything else: one scufris-desktop, one person, one host. The word "service" here means a background process on your own machine, and nothing more. There is no tenancy, no account, no authentication, no network listener, no second device to keep in step. The socket is a Unix socket in your own runtime directory under a private one, so anything that can open it can already act as you — the same reasoning the pill's command socket already runs on.

This is what keeps the service small enough to be worth building. It routes text between three local processes. Every question that starts with "what if two…" is answered by this law rather than by code.

L2 — Nothing is migrated

No backwards compatibility, in any direction. Protocol v3 does not coexist with v2; it replaces it. On-disk state that no longer fits is deleted rather than converted — the job state tree under $XDG_STATE_HOME/scufris/ included. If something breaks, it is made to work on the new arrangement only. There is one user and one machine, and a migration path would cost more than the data is worth.

L3 — The agent keeps working as it does now, plus one change

Jobs, tmux panes, delegation, skills, Calm, response shaping, the .scufris.toml agent menu: all of it stays inside pi and none of it changes shape here. The one file this design touches is the desktop extension, which stops binding a socket and starts connecting to one. The service never learns what a job is.

The one change that does land inside the agent is not this design's: tasks/20260826-183008/TASK.md, Scufris does what is asked, not a workflow (priority 75, tags identity and workflow). It lands independently, and L4 is what it leaves behind. Read the two together: everything the agent does today survives except the fixed pipeline, and nothing here waits on that task or is blocked by it.

L4 — One job, one agent, and no pipeline

The shape task 20260826-183008 leaves the agent in: a request runs the agents it names and no others, and one job has exactly one agent as its interface. Whatever that agent spawns beneath itself is its own business.

That work is separate from this document, but it bounds it. The service routes a conversation, not a workflow: there is nothing in the protocol that knows a request can become several pieces of work, and nothing that would need to change if one did.

01

The inversion

Thesis

Today the Pi process in the Kitty scratchpad is the server. It binds $XDG_RUNTIME_DIR/scufris/daemon.sock, and the desktop companion connects out to it. That is why the Home Manager module asserts that enabling the desktop requires enabling the popup: without the terminal window there is no socket, and without the socket there is no Scufris.

The conversation is therefore pinned to a window. Close the window and the assistant is gone. That is the thing worth fixing, and everything here follows from fixing exactly that.

A new process, scufris-service, becomes the server. It spawns the one agent and owns the session. It serves one socket. Both the agent and the desktop app connect to it. No user interface owns the conversation any more, so no user interface can take it away.

02

Who owns what

Four processes

Four processes, and the boundaries are drawn so that each one can be described in a sentence. What a process does not do matters as much: a service that grew rendering or synthesis into it would be the thing this design is trying not to build.

Process Owns Never
scufris-service The session directory. Spawning and supervising the one agent. The one socket and who is connected to it. The Scufris state. A bounded transcript ring so a reconnecting screen has something to draw. Routing surface commands between the agent and the frontend. No audio. No synthesis. No rendering. No windows. No model calls. No tools. No idea what a job is.
pi --mode rpc The thinking. Tools, sub-agents, skills, jobs, delegation, Calm policy, response shaping. Everything under extensions/scufris/ keeps running here, unchanged except for the desktop extension. Binds no socket. Owns no window. Speaks nothing aloud.
scufris-desktop Every pixel and every sample. The pill, the textbox, the HUD, the tray, the widget runtime. Microphone capture and the whisper client. Piper synthesis and playback. Hotkeys and focus restoration. Holds no conversation. Persists nothing but its own unsent words.
whisper-server Transcription over HTTP. Already a separate unit, already optional, already someone else's if you point at an endpoint. Knows nothing about Scufris.

Putting whisper and piper behind the desktop app is the decision that makes the service simple. The service handles text and only text. It cannot speak, which means a headless service is silent by construction rather than by configuration, and voice becomes a property of the machine you are sitting at rather than a property of the assistant.

The half of this that already works this way is the microphone: capture and the whisper client are in the companion today. The half that moves is piper, which currently runs inside the Pi process. The seam is clean, because the two halves of speech are already separate concerns: shaping stays in the agent, where the voice extension decides what is safe to say aloud and rewrites it into prose, and synthesis moves to the frontend, which is the thing with a speaker. The agent's prose rules do not change and are not conditional on anything the frontend is doing.

03

The seams

Three protocols

Three, and two of them already exist. That is the pleasant surprise of this design: almost nothing new has to be invented, because the protocol work done for widgets was done against the right abstraction.

Seam 1 — service to agent: Pi RPC over stdio

Pi's own documented protocol, LF-terminated JSON lines on the child's stdin and stdout. Scufris already drives it for standalone Quick Review (tools/quick-review-agent), so this is a road we have walked. 

// service -> agent
{"id": "u-41", "type": "prompt", "message": "what is on my calendar"}
{"type": "prompt", "message": "...", "streamingBehavior": "steer"}
{"type": "abort"}

// agent -> service
{"type": "agent_start"}
{"type": "message_end", "message": {...}}
{"type": "tool_execution_start", ...}
{"type": "agent_settled"}

The service is the RPC client. It writes prompts and reads events, and that stream is where the Scufris state and the HUD transcript both come from.

Seam 2 — agent to service: the surface protocol, inverted

Tool calls originate inside a model turn and need an answer. scufris_widget_open has to return a surface identifier before the tool result is written, so it cannot ride the event stream. It needs a request and response channel, which is exactly what extensions/scufris/desktop/ already implements.

So the code stays and the direction flips. server.ts stops calling createServer and starts connecting out to the service, the way daemon.rs does today. The correlation identifiers, the five-second bound, the typed error codes, the well-formedness checks and the shared fixtures all survive. The socket lock disappears, because the service binds the socket and systemd makes sure there is one of it.

Seam 3 — frontend to service: the same socket, a second role

One socket, three kinds of client, declared in the hello: agent, frontend, control. By L1 there is at most one agent and at most one frontend; a second frontend takes the place of the first rather than being fanned out to, which is what makes a companion restart land cleanly instead of waiting on a half-open connection. control is short-lived and there may be several at once, because that is just scufris-ctl running. 

// frontend -> service
{"v": 3, "type": "hello", "role": "frontend"}
{"v": 3, "type": "submit", "id": "u-41", "text": "..."}
{"v": 3, "type": "abort"}
{"v": 3, "type": "widget_event", ...}

// service -> frontend
{"v": 3, "type": "state", "state": "working"}
{"v": 3, "type": "say", "text": "..."}       // already shaped by the agent
{"v": 3, "type": "transcript", "entry": {...}} // for the HUD
{"v": 3, "type": "widget_open", ...}

Note what is not here. The frontend does not report that it is speaking, because nothing outside the frontend needs to know: the pill, the tray and the widget clocks are all in the same process as the speaker. Speaking is a local presentation state layered on top of the Scufris state, not a fact the service tracks. There is no voice flag on the wire either — whether this machine has a microphone is the frontend's business and changes nothing the service does.

The service routes rather than interprets. A surface command from the agent goes out to the frontend and its answer comes back under the same correlation identifier. When no frontend is connected the service answers companion_unavailable itself, which is a code the widget tools already handle.

scufris-ctl is the control role, which gives it real verbs for the first time: send, listen, cancel, abort, state, detach, attach. It works with no graphical session at all, which is how the service gets tested without a display and how the conversation stays reachable over ssh.

04

What the stream gives us for free

Read before building

Pi's RPC events answer several questions that Scufris currently answers with code of its own. Reading the event table before writing the service removes work rather than adding it.

The state stops being computed, and gets a name

agent_start, tool_execution_start and agent_settled are the state machine. The service maps them onto one small ScufrisState enum — idle, working, attention, detached, error — and that enum is what crosses the socket. The frontend never parses a Pi event and never learns Pi's vocabulary, so an event Pi adds tomorrow is a service change and nothing more.

Speaking and listening are deliberately not in that enum. They are what the frontend is doing, not what the assistant is doing, and the frontend layers them on top of the state it was given. That is the answer to "should the service know it is speaking": no, and not knowing is what keeps it out of the audio path.

Talking over a running turn gets a real answer

streamingBehavior: "steer" delivers a message after the current turn's tool calls and before the next model call; "followUp" waits for the run to settle. So one rule covers everything: the activation key always means listen. What you say is an ordinary prompt when the assistant is idle and a steer when it is working, and neither case needs a different key or a different window.

Barge-in falls out of the same rule

Pressing the activation key while Scufris is speaking stops the playback and opens the microphone. The frontend owns both the speaker and the key, so this is a local decision with nothing crossing the socket: cut the piper process, drop to listening, and let whatever is said land as a prompt or a steer by the rule above. Interrupting is how people talk, and it should not require a second gesture.

Stop is now possible

abort ends the current run. There is no way to do that from the pill today. It becomes a verb on the ctl and a key on the frontend.

The HUD's history has a source

message_end carries complete messages, and get_entries fetches session history on demand. The service keeps a bounded ring for the common case — a frontend restarting needs the last screenful, not the last month — and asks the agent for anything deeper.

One thing that must not be skipped

In RPC mode, extension user-interface requests (notify, confirm, input, select, editor) are emitted on stdout and wait for an answer on stdin. Today the TUI answers them. If the service does not, an extension that opens a dialog hangs the agent.

Scufris extensions currently use only notify, which is fire-and-forget, so the immediate exposure is small. The service must still answer every request type — routing what it can to the frontend and replying with a cancellation for the rest. And notify stops being a line in a terminal nobody is looking at and becomes a tray notification, which is an improvement worth taking on day one.

05

Surfaces

Voice is a capability

Voice is not a mode and the HUD is not the other mode. Voice is a capability — whether this machine has a microphone and a speaker — and the surfaces are chosen to suit it. Reading the transcript while talking stays an ordinary thing to want.

Surface What it is Keyboard
Pill The orb, and the priority. An indicator and nothing else: listening, working, speaking, attention, detached, disconnected. It has no keys of its own any more. Never focused
Textbox What voice submissions pass through: the transcription arrives in it and is read before it is sent. Voice only — with no microphone there is nothing for it to review, and typing belongs where the conversation already is. Takes focus
HUD What Super+S opens today, rebuilt as our own window: the Calm conversation drawn from the transcript stream, with the input line for typing. Deferred until we want it. Takes focus
Widgets Unchanged. The runtime stays in the frontend; its commands arrive through the service instead of directly. Never focused

Voice never submits directly. Recording fills the textbox and the textbox sends, so you always read the words before they go. The recording state and the review state collapse into one window, and the frontend has exactly one path from text to submit. The cost is honest: voice submission becomes two keypresses plus Enter, where today Enter while recording sends immediately.

Until the HUD exists, typed input is scufris-ctl send. That is a deliberate ordering, not an oversight — the pill is the surface worth having first, and a machine with no microphone is not the case being optimised for.

06

One turn, keystroke by keystroke

Interaction
Super+D

Always listen. Nothing up: pill rises, microphone opens. Listening: stop, transcribe, open the textbox with the words in it. Speaking: cut the speech and listen again.

Super+Escape

Cancel the listen. Discards the recording and puts the pill back to rest.

Enter / Escape

In the textbox only, which holds the keyboard, so these are ordinary keys in a focused window. Send, or discard.

Two properties fall out of this. The service never needs a display, so the whole conversation path is testable with scufris-ctl send and no graphical session. And the frontend never needs the agent, so it can start, show a disconnected orb, and connect when the service comes up — which is what it already does today with daemon.rs.

07

What this deletes

Subtraction

A design that only adds is a design to distrust. This one removes several pieces of machinery that exist purely because the socket is in the wrong process or because the pill has to steal the keyboard. Under L2 they are deleted rather than deprecated.

  • The Kitty popup, and its systemd unit. Retired in the same increment that stops needing it, not kept around as a fallback.
  • The i3 binding mode. All of keys.rs, the SCUFRIS_DESKTOP_MODE_COMMAND hook, the mode-enter and mode-leave dance, and the documentation explaining it. Bare Enter and Escape only ever needed rescuing because the pill wanted keys without holding the keyboard. The textbox holds the keyboard, so they arrive normally.
  • desktop.sock and command.rs. The companion stops being a server. scufris-ctl accept and the scufris://accept page round trip go with it.
  • The socket lock. tools/desktop/scufris-socket-lock exists because two popups could race for one socket name. A systemd service does not race with itself.
  • SCUFRIS_DAEMON and the server half of the desktop extension. Roughly the accept loop and the lock dance; the protocol and the command machinery stay.
  • Protocol v2. Replaced, not versioned alongside. The fixtures move with it.
  • The Home Manager assertion that the desktop requires the popup, along with the popup's own options.
  • The review window as a separate state, which becomes the textbox.
  • Stale state on disk. The job tree under $XDG_STATE_HOME/scufris/ and the companion's pending transcript are deleted rather than converted.
08

No terminal, and no attaching one

Answered

Asked three times on revision 1: can a pi TUI attach to a running pi --mode rpc, given its PID or otherwise?

The answer is no, and it is not close

Checked against the installed package: the CLI has no attach verb, the RPC documentation describes no socket or multi-client mode, and nothing in dist implements session sharing. RPC mode is bound to the stdin and stdout of whoever spawned it, one client, for its lifetime. A second pi pointed at the same session file would be a second writer, which is the one thing that must never happen.

This is the real cost of the design and it should not be soft-pedalled. The Kitty popup is a complete Pi terminal: model cycling, thinking levels, slash commands, session forking, the config UI, scrollback, copy. Retiring it costs all of that, and the HUD will not match it for a long time.

Two things are possible, and both are worth having.

  • An explicit handoff. scufris-ctl detach stops the service's agent child and leaves the session directory free; you then run an ordinary pi --continue in any terminal against it and get the whole TUI back. scufris-ctl attach restarts the child when you are done. The service reports detached as a state, so the pill says so rather than looking broken. This needs no systemd unit and no popup: it is two ctl verbs against a service that already supervises the child.
  • A read-only live view. Pi appends the session as JSONL and publishes the path as PI_SESSION_FILE, so tail -f on it is a working, if raw, live transcript with no second writer. Useful today, and useful later as a check on whatever the HUD renders.

The service becomes the single point

Today a companion crash is harmless and a popup crash takes the socket with it. Afterwards both frontends are disposable and the service is the thing that must not die. That is the trade being bought deliberately: one process to supervise, restarted by systemd, with the session on disk so a restart resumes rather than forgets.

09

Decisions

Settled on revision 1

D1 — The frontend is its own unit

The service does not spawn the Tauri app. A graphical client needs the display environment and must die with the graphical session, which PartOf=graphical-session.target already models; a service on default.target spawning a GUI child fights that. The service still owns the relationship, because it is the only server the frontend has.

Settled: two units, one Home Manager surface. The flake exposes a single output for configuring Scufris and wires whatever units it likes underneath — the split is an implementation detail of the module, not something to configure twice.

D2 — Rust, unless it has to be an extension

Settled: Rust for the service and everything native. TypeScript only where the code must run inside Pi as an extension. That keeps us coupled to Pi's documented protocol rather than to Pi's internals, and pi keeps doing everything its CLI does today.

D3 — The workspace is renamed

Settled: desktop/ becomes native/, holding scufris-control (protocol), scufris-service, and scufris-desktop. One rename, done in the increment that adds the second crate.

D4 — Nothing is kept as a fallback

Settled: the popup unit is retired outright. The HUD is built when we want it, not as a precondition. The pill is the surface that matters, and detach covers the terminal case in the meantime.

D5 — Speech shaping does not move

The confusion on revision 1 was mine. The question was never whether the agent decides what to say aloud — it does, exactly as now, and its prose rules apply regardless of what is listening.

Settled: the agent shapes and marks text as speakable, and that travels as a say command because speaking is an act with a lifetime that the frontend must be able to refuse — muted, no speaker, no voice. The frontend synthesises it if it can and drops it if it cannot, and the service is not told either way.
10

Increments

Order of work

Five, and the shape is set by L2: with no backwards compatibility, the socket cannot move in two steps. The switch is one commit, and it is the only one that leaves nothing working in between.

  1. The service, headless. Rename the workspace to native/. New Rust crate that supervises one pi --mode rpc, owns the session directory, maps events onto ScufrisState, holds the transcript ring, answers extension UI requests, and serves protocol v3 with three roles. scufris-ctl send | state | abort | detach | attach. Nothing graphical changes and the old arrangement keeps working beside it, so this lands and is exercised on its own.
  2. The switch. One commit: the desktop extension becomes a client, the frontend becomes a client, piper moves into the frontend, and desktop.sock, command.rs, keys.rs, the socket lock, SCUFRIS_DAEMON, protocol v2, the popup unit and its Home Manager options are all deleted. Afterwards there is one socket and one server.
  3. The textbox. One focused window that voice submissions pass through. The review state and Enter-while-recording are deleted with it.
  4. Listening is one rule. The activation key always listens: barge-in cuts the speech, and a submission during a run goes as a steer. Abort gets a key.
  5. The HUD, when we want it. The Calm conversation as a frontend surface with the typing line, drawn from the transcript stream, with get_entries behind it for depth.

The widget runtime is untouched by all five. It stays in the frontend, its protocol survives with one more hop in front of it, and the four tools do not change shape. Jobs, tmux, delegation and the agent menu are equally untouched: they live inside the agent and never knew where the socket was.
