scufris · hud · protocol 7

Receipts, offers and job rows

Measured facts as badges under the message, cited by job. Offers as badges that run. Jobs as a list at the foot of the chat that holds every row until you file it. Settled and ready to build; the mockups below work, so take an offer, stop a job, clear the list.

settled

Decided

  • Badges go at the foot of the message, grouped by job. One wrapping rank per job, led by that job's id. The id does the binding, so the prose never has to be parsed and never has to be broken.
  • An offer is a control. Click it and it runs. It sends for job <id> do <thing> behind the scenes and puts no user line in the chat.
  • A job holds its row until it is filed. Finishing does not remove it. A live row can be stopped; a finished row can be archived.
  • The job list scrolls away. It is the last item in the conversation flow, not a sticky floor.
  • The tray keeps its one aggregate word, derived on the host from the rows rather than sent as its own field.
  • Cancel arms before it fires. The mistake costs an hour of an agent's work and the guard costs a click.
  • Live rows never drop. At the cap of 8 the oldest terminal rows fall off the top. They are still in scufris-jobs.
  • Spent is recorded with the conversation entry, so a reconnect cannot re-arm a button for finished work. The one store change in this design.

offers

What a click does

The badge carries a stored prompt the model wrote. Clicking submits for job 750a4de8a80d: push master as a turn, and the surface never writes that string: the extension composed it when it built the offer, so the button ships an id and nothing else.

No user line appears. What appears is the answer, and above it the badge you pressed, now spent. That mark is doing real work: it is the only thing in the window that says what the reply is replying to. Try it.

scufris enter sends · + attaches · esc closes
scufris Landed it as 75919d8, and it is not on the remote yet. 750a4de8a80d landedyes pushedno
>

Spent is permanent and recorded against the offer's id, so a reconnect does not hand back a live button for work already done. That is the one thing here the conversation store does not hold today.

jobs

The row outlives the job

A finished job keeps its row and its last words, so an overnight run is still there in the morning. Filing it is the acknowledgement, and it is what clears it.

One control per row, and which control it is tells you the state before you read it. A live job can only be stopped, so it shows a red x. A finished one can only be filed, so it shows clear. Both work below.

scufris enter sends · + attaches · esc closes
scufris The night finished. Two of the four groups it opened are still running.
jobs

x arms before it fires: one click turns it into sure? for three seconds. Stopping the wrong job costs an hour of an agent's work, and the two-step costs a click. clear the N finished appears only when two or more rows are terminal.

Which makes the tray honest

The aggregate word is derived from the rows, and a failed row holds. So the tray stays red after a job fails at 03:00 and goes quiet when you file it, rather than when the process happens to exit. Acknowledgement, not timing.

protocol

What version 7 carries

SERVICE_VERSION is 6, and read_exact at shared/control/src/service.rs:422 rejects any other version outright — no negotiation, no ignoring unknown fields across versions. Desktop, phone (ios/Sources/Protocol.swift:3) and scufris-ctl move together, and that cost is the same for one field or four. 

agent.response
  text, details?, widgets?, attachments?
+ receipts?: Citation[]       // at most 4, one per job

Citation { job_id: string,
             badges: Receipt[],   // at most 6
             offers: Offer[] }    // at most 2

Receipt  { label, value,
             state: "measured" | "refuted" | "claimed" | "unknown" }
Offer    { id, label }          // the prompt stays host-side

agent.jobs                    // replaces agent.state
  jobs: JobRow[]              // at most 8, replayed on connect

JobRow   { id, project, since, summary,
             state: "working" | "blocked" | "done" | "failed" }

job.command                   // surface -> host -> extension
  { id, action: "cancel" | "archive" }
offer.take
  { id }                      // the host submits the stored prompt

Offers sit inside the citation because every offer follows from a receipt, and the strip is where they are drawn. An offer with no job has no place to go, which is a constraint worth having.

agent.state goes. Today every surface gets one aggregate word — failed, blocked, clear — and one detail string (service/index.ts:47-55). The tray still wants that word, so the host folds the rows down to it. One source, two readings.

No model writes a badge

The rule the whole thing rests on. The extension builds every Receipt from the helper's own receipt.facts, receipt.claims and receipt.unavailable, exactly as receipt_sentences does at tools/jobs/scufris-jobs:3467. The four states are that vocabulary and not a second one:

landedyes pushedno testsclaimed, not verified releasenot measured

measured = the fact is true · refuted = measured and false · claimed = the worker said it and no fact backs it · unknown = it is in unavailable with a reason, and is never drawn as a no.

The offer is the exception, and the only one: the model chooses it and writes its prompt. That is why it is the badge that looks like a control.

the phone

What iOS does

The same shapes SwiftUI already has. A strip becomes a wrapping run of capsules under the bubble, one run per job, with the same four state colours. The job list becomes a section above the composer, and the row control becomes a swipe: swipe a live row to stop it, a finished one to file it, which is the gesture the platform already teaches. The blocked notice at ContentView.swift:1134 goes: it was the aggregate, and the rows say the same thing with names on it.

for the record

What was dropped

Inline badges

Badges flowing inside the sentence, like a link. Kept the evidence closest to the claim, but three or four marks in a paragraph is a paragraph you stop reading, and a badge can land on a line break and split the sentence.

Strips spliced into the prose

The message broken at the sentence that names each job, so a strip sat immediately after its claim and needed no label. It bought a shorter badge and cost a byte offset in the protocol, a sentence-boundary search over the model's prose, a fallback for when the model did not name the job, and four blocks of height for two sentences. The job id does the same binding for one token.

The sticky floor

A job list pinned to the bottom of the scroller so a running job stayed on screen. Cost about 46px of a 560px window permanently, and it would have been the first chrome this window owns that is not a message.

build order

Four steps, each shippable

  1. Protocol 7 across the three surfaces. The version bump is lockstep and pays for everything after it, so it goes first and alone: the fields land, nothing draws them yet.
  2. Citations on the desktop. The extension folds receipt.facts, claims and unavailable into badges; the HUD draws the strip. Read only, no controls, no store change.
  3. Job rows, then their controls. agent.jobs replaces agent.state and the tray folds the word. Rows draw first; cancel and archive follow, because they need job.command to reach the extension.
  4. Offers. Last, because it is the only step that touches the conversation store: the prompt kept host-side, and spent recorded per offer id.
