# Plan: the user-level config file

Plan for task `20260908-145550`. Agreed with Alex on 2026-09-08.

## Scope

One user-level config file, the reader for it, and the first source that uses
it. No TypeScript and no Rust: the extension calls the helper and gains no
tool, so this is Python, Nix, and documentation.

## How this got here

The task it came from asked for built-in sources: a source kind the helper
runs itself, with a `jobs` one first, and a per-project flag to opt into job
stats. None of that is built.

A built-in source is a second kind of thing to learn and a second kind of
thing to add to. The reason it looked necessary was that a jobs source has no
project to belong to, and a source was defined as a project. Letting a source
be declared for the machine removes the reason, and the jobs source becomes an
ordinary source with an ordinary prompt.

The per-project flag is gone for the reason Alex gave: a briefing that grows a
key for every kind of content is the wrong shape, and the jobs table is not
about any one project anyway.

## Decisions

- The jobs helper reads the user file, not `briefing.py`. `declared_sources`
  already delegates so that project discovery and `.scufris.toml` have one
  owner. What a source is, is the same question, so `briefing_entry()`
  validates a user entry and a project entry identically. A second parser
  would be a second answer.
- The reader assigns slugs and callers stop deriving them. `stamp()` computes
  the contribution filename from the project ID today, so a user section named
  `scufris2` would take the `scufris2` project's file. The reader namespaces
  user sources, and a collision stops being expressible rather than being
  checked for.
- `project_root` becomes `root`. A user source has no project and `ask()`
  only wants a working directory. Without a declared `root` a user source runs
  in `$HOME`, which is right for anything reading XDG state.
- A named config that is missing is a refusal. A missing default path is not.
  `--config typo.toml` quietly yielding no sources is a morning discovered too
  late; a machine that never configured one is the ordinary case.
- A malformed user file costs the user file only. One diagnostic naming it,
  and every project source still contributes, exactly as a malformed project
  file behaves now.
- The Nix option declares the known keys over a freeform type. Build-time
  validation is the reason to generate the file at all, but the reader will
  learn a key before the module does, and that must not be a rebuild-blocking
  mismatch.
- The helper reads a TOML path and does not know Nix exists. Home Manager is
  one way to produce the file. Anyone else writes it by hand, and a reader
  that depended on something only the module can produce would have stopped
  being a program.
- The jobs source is guidance, not code. The helper measures and the prompt
  reports, which is the division receipts already established: `SKILL.md`
  tells the foreground to quote the verdict rather than asking the model to
  compute it.
- The file is briefings-only, and the documentation says so. A project keeps
  its own `[conventions]` and `[agents.*]` even where that duplicates another
  project, because a checkout has to work for someone whose machine has none
  of this.

## The file

```toml
# ~/.config/scufris/config.toml, generated by Home Manager

[briefings.morning.jobs]
description = "What Scufris did overnight."
keywords = { harness = "pi", thinking = "medium" }
guidance = """
Read what the helper measured. Do not judge whether work is done; the receipt
already says.
...
"""
```

`[briefings.<profile>.<name>]`. Names are required at user level: there is no
project name to slug, and no existing shape to be ambiguous with. An optional
`root` says where to run.

## Build order

Each step is checkable on its own.

1. The reader, in `tools/jobs/scufris-jobs`. Resolve
   `$XDG_CONFIG_HOME/scufris/config.toml`, parse `[briefings.<profile>.<name>]`,
   reuse `briefing_entry()` (`:600-627`), assign unique slugs, resolve `root`.
   An optional `config` key on the `briefings` request and its
   `validate_request` set (`:663`).
2. The consumer, in `tools/briefing/briefing.py`. `stamp()` reads the slug
   instead of computing it; `ask()` uses `root`. `--config` in `cli.py` and
   `SCUFRIS_CONFIG` in the environment, the flag winning over the variable.

   Steps 1 and 2 together are shippable: a user source contributes.

3. The Home Manager option:
   `programs.scufris.agent.briefing.sources.<profile>.<name>`, a sibling of
   `profiles` rather than a key inside one, so the timer-shaped boundary from
   task 20260908-140024 still holds. Rendered with `pkgs.formats.toml`.
4. The watermark. `previous_finished(profile, date)` reads back over the kept
   runs for the newest run of that profile, and `contribution_prompt` (`:294`)
   carries its finish time. Computed once per run. The first run of a profile
   says there was no previous one, rather than leaving a model to invent a
   window. This is the step that changes the prompt every existing source
   already gets.
5. The archived-job listing, over both `jobs_root()` and `archive_root()`,
   returning records since a timestamp with their newest receipt. Reuses
   `load_job(..., archived=True)` (`:1485`) and `stored_receipts` (`:3185`).
   Surfaced in `scripts/scufris-jobs` so a source can call it.
6. The jobs source itself, as guidance: quote receipt fields verbatim, say
   "claimed, not verified" for an unbacked claim, say "not landed" in those
   words, and put the jobs in a Markdown table.
7. Documentation. `docs/src/dev/briefings.md` gains a second kind of
   declaration and loses "a source is a Git project";
   `docs/src/guide/configuration.md` and `docs/src/reference/environment.md`
   gain the option and `SCUFRIS_CONFIG`; `CHANGELOG.md`.
